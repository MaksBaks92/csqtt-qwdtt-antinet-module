# AntiNet Protocol Module API (`apiVersion: 1`)

Как написать **протокол-модуль** для AntiNet: добавить поддержку нового wire-протокола, data-plane
которого не вкомпилен в AntiNet, **без пересборки приложения**. Модуль — **скачиваемый файл в
каталоге модулей, не приложение и не APK** (§2.1); AntiNet остаётся протокол-агностичным и знает
только этот API и SOCKS5.

> Пути в этом документе — относительно корня архива (где он лежит). Карта папки и быстрый старт
> — `README.md`; внутренности AntiNet-стороны и кроссплатформенный порт — `PORTING.md`; обновление
> вендоренного апстрима — `UPGRADE.md`.
>
> **Минимальный скелет** (копируйте как шаблон) — `examples/moduleecho/`: тривиальный
> passthrough-модуль, показывающий ровно обязательную обвязку — `module.json`, helper с SOCKS5 на
> хостовом сокете, protect-fd, маркер `ready` и сабкоманды `summarize`/`normalize`. Замените схему,
> парсер и тело dial'а на свой протокол. **Полный рабочий пример** — `(репозиторий AntiNet) examples/modulemasterdns/`
> (StormDNS, DNS-туннель). Сборка helper'а — `build.py` (единый вход под любую ОС;
> `tools/build-module.py` — его низкоуровневый android-only слой, напрямую не нужен), см. §5.

## 1. Модель (зачем так)

```
AntiNet (sing-box) ──SOCKS5──► helper модуля ──► интернет
                               Android: .so, dlopen в зарезервированный слот-процесс
                               Desktop: форкнутый бинарь
                               оба: под UID AntiNet, freeze-immune, egress мимо TUN
```

- **Модуль — это каталог с дескриптором и артефактом**, скачиваемый: `.so` (`-buildmode=c-shared`) на
  Android, исполняемый файл на Desktop. Приложением (APK) модуль не является.
- AntiNet находит модуль сканом своего каталога модулей, поднимает его в **отдельном процессе**
  (Android — зарезервированный слот-процесс через `dlopen`; Desktop — форк) и гонит трафик в его
  **SOCKS5**, слушающий сокет для которого создаёт сам (§2.6).
- AntiNet не декодирует формат ссылки — вся специфика протокола живёт в модуле.

**Почему отдельный процесс, а не in-process:** два Go-рантайма в одном процессе крашатся
(`crosscall2`, `JNI_OnLoad`). Плюс для сторонних модулей это ещё и граница отказа: краш чужого кода
не уносит туннель целиком.

**Почему на Android `.so`, а не исполняемый файл:** W^X и SELinux на API 29+ запрещают `execve`
скачанного файла из `filesDir`, а `dlopen` разрешают (проверено живьём на API 35). Отсюда
`c-shared` вместо PIE.

## 2. Что предоставляет модуль (контракт)

### 2.1. Дескриптор `module.json` — единый для обеих платформ

Модуль — это каталог с дескриптором и бинарём. **Модуль не приложение**: на Android он ставится как
скачанный файл, без package-installer'а, подтверждений установки, `<queries>` и discovery через
`queryIntentServices`. Секция `android` (`applicationId`, `service`, `actionActivity`) в дескрипторе
**игнорируется**: объявлять её не нужно, интерактивные действия рисует сам AntiNet (§2.7).

**Куда кладётся.** Android — `filesDir/modules/<id>/`, Desktop — `<exe>/modules/<id>/`. Имя каталога
`<id>` и есть **стабильная идентичность** модуля: ключ пользовательских настроек, оверрайдов
таймингов и состояния.

```jsonc
{
  "apiVersion": 1,                      // единственная выпущенная версия контракта (см. § «Версионирование»)
  "schemes": ["myproto"],               // схемы без "://"
  "name": "My Protocol",                // карточка «Модули» + chip-имя протокола
  "description": "Что это и зачем",
  "homepage": "",                       // человеческая страница/репо
  "updateUrl": "",                      // JSON-манифест версии → тихое автообновление (§2.5)
  "version": "1.0.0",                   // единственная версия: и показ, и сравнение (§2.5)
  // "bundleTarget": "arm64-v8a",       // ⚠ пишет сборщик, не автор: подпись арки бандла (§2.5)

  // Бинарь на каждую платформу. Ключ `android` — имя `.so`, `desktop` — имя исполняемого файла.
  // Объявляешь только те платформы, которые реально поддерживаешь.
  "helperBinary": { "android": "libmyhelper.so", "desktop": "myproto-helper" },

  "handoverMode": "restart",            // "signal" | "restart" (§2.8)
  "hostEvents": ["handover"],           // какие ПРИЧИНЫ события модуль разбирает (§2.8); не объявил → только handover
  "parallelPing": false,                // допускает ли схема несколько live-сессий разом
  "pingWhileConnected": false,          // true → пинг не выселяет коннект: у него своя сессия (§2.10)
  "socks5": true,                       // у helper'а наш generic SOCKS5-фронт (§4, канон-инъекция)
  "socks5Udp": true,                    // транспорт несёт произвольный UDP, то есть socks отвечает на UDP ASSOCIATE (§6).
                                        // ⛔ CONNECT-only модуль обязан объявить false: хост тогда отправляет
                                        // "network":"tcp" у его socks-аутбаунда, и ядро отбивает UDP до дозвона.
                                        // Молчание = true, и тогда QUIC приложений идёт в модуль, тот отвечает
                                        // 0x07, а трекер здоровья считает это отказом дозвона и дёргает
                                        // исправный модуль (замер: fails=9/3 → FIRE … code=7)
  "dnsResolver": true,                  // helper резолвит свои dial-цели off-tunnel (§4, канон-инъекция)
  "relayWindowSec": 15,                 // только для модулей с релейным слоем (§2.10); иначе опустить

  // Lifecycle-тайминги — значения по умолчанию, пользователь их редактирует в карточке «Модули» (§2.10).
  "crashLoopMaxDeaths": 5, "crashLoopWindowSec": 15,
  "heartbeatSec": 120, "handoverDebounceSec": 2,
  "pingTimeoutSec": 20,                 // потолок одного пинга конфига этой схемы (§2.10)
  "pingNeedsConsent": false,            // true → перед фоновым пингом хост спросит `canping` (§2.2/§2.10)

  "settings": [ /* декларации настроек, §2.11 */ ],
  "build":    { /* как собрать, §5 */ }
}
```

**`parallelPing=false`** (рекомендуется) → AntiNet пингует конфиги модуля последовательно, по одной
живой сессии на схему. `true` нужен, только если схема реально допускает несколько одновременных
сессий.

⛔ **`true` — это обязательство модуля, а не подсказка хосту.** Объявив его, helper обязан
выдерживать несколько своих экземпляров одновременно: занятый внутренний порт — не повод падать
(брать эфемерный), файлы состояния — только внутри выданного `profileDir` (у каждой сессии он
свой), общих на схему замков и сокетов быть не должно. Хост со своей стороны заводит по сессии на
ссылку и держит их каталоги раздельно; сколько их поднимется разом — ограничено лишь свободными
слотами пула за вычетом одного, зарезервированного под коннект.

#### `pingWhileConnected` — отдельная сессия под пинг

Два этих ключа решают одно и то же: **сколькими живыми сессиями схемы хост вправе пользоваться**.
Ключ сессии выводится из них, и форм ровно три — одинаково на обеих платформах
(`ModuleManager.pingSessionKey`, `modulemanager.pas::PingKey`):

| объявлено | ключ сессии | что это значит |
|---|---|---|
| ничего | `<схема>` | пинг делит сессию с коннектом: пинг соседней ссылки той же схемы при живом коннекте пропускается |
| `pingWhileConnected: true` | `<схема>#ping` | пинг получает свою сессию и **не выселяет коннект**; пинговая по-прежнему одна на схему |
| `parallelPing: true` | `<схема>#ping#<отпечаток ссылки>` | сессий столько, сколько ссылок |

`parallelPing` подразумевает и разделение с коннектом — его форма всегда несёт `#ping`: иначе
«несколько сессий» означало бы, что одна из них коннектная, а выселять её пинг права не имеет.
Пинг уже подключённого конфига второй сессии не заводит ни в одной из форм: хост сначала смотрит
коннектную сессию по той же ссылке.

Объявлять `pingWhileConnected` стоит, когда протокол выдерживает вторую параллельную сессию, но не
произвольное их число, — например когда сервер лимитирует подключения устройства, а не ссылки.

**Неизвестные ключи игнорируются** — и это стоячее правило, а не поблажка: дескриптор от более новой
версии AntiNet не должен ломать разбор на старой, и наоборот.

#### Конфиг неизвестной схемы = модульный

Если пользователь добавляет конфиг со схемой, которой нет ни у одного встроенного протокола и ни у
одного **установленного** модуля, AntiNet **не выбрасывает его**, а сохраняет как модульный: сырая
ссылка кладётся в `ext.moduleLink`, конфиг помечается «нет модуля» и на попытку подключения честно
отвечает «модуль не установлен» (а не молча умирает как мёртвый сервер, и **не** помечается мёртвым
пингом — конфиг-то исправен). Поставят модуль — его handler перехватит ту же ссылку на следующем
разборе и заполнит имя и сервер по-настоящему.

Практический смысл: подписку с конфигами вашего протокола можно добавить **до** установки самого
модуля — обычно именно в этом порядке всё и происходит.

### 2.2. Весь декод — в Go-helper'е, без единой строчки Kotlin

**Декод формата ссылки полностью в helper'е** — кроссплатформенно (1:1 Android ↔ Desktop, ни на одной
стороне нет JVM-glue). Точки декода — **сабкоманды** (Desktop: форк с argv[1]; Android: тот же verb
через `antinet_module_call`, ответ строкой — см. §2.3):

| Сабкоманда | Вызов | stdout | Назначение |
|---|---|---|---|
| `summarize` | `helper summarize <link>` | 2 строки: `name`\n`server` | сводка для карточки конфига, чтобы конфиги модуля **отличались**, а не выглядели как «myproto:0». На сбой или чужую схему — две пустые строки, AntiNet оставит плейсхолдер схемы. `name` — имя из ссылки (нет — домен или идентификатор); `server` — домен или адрес (порт AntiNet скрывает, если ≤ 0). |
| `normalize` | `helper normalize <raw>` | 1 строка: канонический `scheme://`-link (или пусто) | импорт форм, которые ссылкой не являются: JSON, base64 из файла (§2.6). Узнал свой формат — отдаёт канонический link; чужой формат или уже готовая ссылка — пусто. |
| `canping` | `helper canping <link>\n<profileDir>\n<stateBlob>` | 1 строка: `ok` / `no` | **обязательна, если объявлен `pingNeedsConsent`** (иначе не зовётся вовсе). Отвечает на вопрос «может ли модуль сейчас пинговаться без интерактива?» — фоновой волне показать диалог некому. Аргумент — три строки через `\n`, симметрично тому, как `summarize` их отдаёт; где живёт состояние, решает сам модуль: `profileDir` (переживает перезапуск) либо блоб `MODULE_STATE` (§2.3). Ответ приходит строкой, а не кодом возврата: на Android кода возврата нет вовсе, ответ приезжает строкой из `antinet_module_call`. ⛔ **Хост fail-closed на любую неудачу**: нет бинаря, спавн или чтение упали, ответ пустой — всё это «нельзя». Отсутствие «да» не равно «да», а не ответить модуль может ровно по той причине, по которой его и не стоит пинговать: helper не поднимается. |
| *(коннект)* | `antinet_module_run(...)` / `main()` + argv | — | data-plane (§2.3). Конфиг приезжает **содержимым** (C-строка либо `ANTINET_MODULE_CONFIG`), формат — пары `KEY=VALUE` и сырая `LINK`; helper **самодекодит** ссылку своим парсером. |

- **`summarize`, `normalize`, `canping`** — чистый парсинг: без Go-рантайма data-plane, без сети, без
  побочных эффектов. Отработали — сразу `os.Exit`. Хост зовёт их синхронно и читает stdout с
  таймаутом; `canping` вправе прочитать своё состояние (`profileDir` или блоб из §4), но не сеть.
- **Самодекод конфига** (коннект-путь): helper при старте берёт конфиг содержимым (C-строка либо
  `ANTINET_MODULE_CONFIG`, формат `KEY=VALUE` плюс `LINK`, §2.3), декодирует `LINK` тем же парсером,
  что `summarize`, и берёт SOCKS5-креды и порт из `LISTEN_PORT`, `SOCKS_USER`, `SOCKS_PASS`. Логику
  декода держите в одной Go-функции, которую переиспользуют все точки.
- **Никакого Kotlin-`SubprocessEntry`** — он удалён: был дублёром Go-логики на Android и
  кроссплатформенно невозможен, у Desktop нет JVM. Модуль — это дескриптор плюс Go-код с этими
  точками декода.

### 2.3. Helper — бинарь (Desktop) / `c-shared`-библиотека (Android)

**Две формы поставки, один контракт.** Различается только то, что диктует ОС; всё остальное —
буквально один и тот же Go-код. Ориентируйтесь по таблице, прежде чем читать детали ниже:

| | Android | Desktop | Почему различается |
|---|---|---|---|
| Форма артефакта | `.so` (`-buildmode=c-shared`) | исполняемый файл | W^X с API 29+ запрещает `execve` скачанного файла, но не `dlopen` |
| Точка входа | C-ABI `antinet_module_run(...)` | `main()` + argv | следствие строки выше; тело — общая `realMain(...)`, argv-разбор только в native-входе |
| Запуск | слот-процесс + `dlopen` через шим | форк процесса | изоляция в обоих случаях настоящая, процессная |
| Доставка конфига | C-строка `configContent` | base64 в `ANTINET_MODULE_CONFIG` | §3: секреты не касаются диска; формат текста одинаков |
| Передача сокета | параметр `listenFd` | наследование fd (`ANTINET_LISTEN_FD`); Windows — только `LISTEN_PORT` | обе ОС умеют, API разные; на Windows передать сокет нечем |
| Уведомление модуля | `antinet_module_event("<причина>")` | построчный **stdin** (`<причина>\n`, тот же канал, что `ACTION_RESULT\|…`) | в слот-процессе сигналы недетерминированы (ART блокирует маску на своих потоках); на десктопе сигналы не нужны — канал уже открыт и работает на всех трёх ОС (§2.8) |
| Смерть родителя | слот сам себя реапит в `onDestroy` (плюс AM и биндинг) | стартовый свип хоста `CleanupOrphanHelpers` | `PDEATHSIG` не работает ни там, ни там — см. ⚠ ниже |
| Защита от OOM | выставляет хост (`BIND_IMPORTANT`) | Linux — хост через `oom_score_adj`; Windows — недоступно | слот не форкнутый ребёнок, `oom_score_adj` ему недоступен |

**Одинаково на обеих платформах**: формат конфига (`KEY=VALUE` плюс `LINK=`), stdout-протокол
(`PROGRESS|`, `LOG|`, `ACTION_REQUIRED|`, `ACTION_CLOSE|`, `STATE_SAVE|`, `STATUS|`, `EVENT_ACK|`),
маркер `ready`, контракт восстановления (`START_REASON`, `MODULE_STATE`), off-TUN как обязанность
модуля, разбор SOCKS5, self-heal, декод ссылки.

> ### ⚠ Пять вещей, которые решают форму helper'а
>
> **1. Android: модуль — не процесс, а библиотека.** Скачанный файл на Android запустить нельзя
> (W^X с API 29+ бьёт по `execve` любого writable-файла), но `dlopen` под этот запрет не попадает.
> Поэтому под Android модуль собирается `-buildmode=c-shared`, а AntiNet грузит `.so` в
> зарезервированный слот-процесс и зовёт **плоский C-ABI**:
> ```c
> int antinet_module_run(const char* configContent, const char* resolversPath,
>                        const char* profileDir,   const char* protectPath, int listenFd);
> int antinet_module_event(const char* event);              /* опционально */
> const char* antinet_module_call(const char* verb, const char* arg);  /* опционально */
> void antinet_module_free(const char* p);                  /* парная к call */
> ```
> `antinet_module_run` блокирует, как `main()`. Знать `jni.h` и `JNIEnv` не нужно — маршалингом
> занимается шим AntiNet. **На Desktop** — обычный форкнутый процесс с argv.
> ⚠ Сами вы этих экспортов не пишете: обе точки входа — канон (`shared/entry/entry_android.go` и
> `shared/entry/entry_native.go`), `build.py` инжектит их безусловно. Ваша часть — две функции,
> которые канон зовёт: `realMain(...)` и `moduleCall(verb, arg)`.
>
> **2. Конфиг приезжает содержимым, а не путём.** Секреты (`SOCKS_PASS`, апстримный секрет внутри
> `LINK=`) не должны касаться диска: `data/`-дерево на Desktop world-readable, на Windows
> ACL-permissive. Desktop — base64 в переменной окружения `ANTINET_MODULE_CONFIG`; Android — прямо
> C-строкой. Формат текста — KEY=VALUE + `LINK=` (§ ниже):
> ```go
> // desktop: содержимое приезжает переменной окружения, путь-аргумент — фоллбэк
> if enc := os.Getenv("ANTINET_MODULE_CONFIG"); enc != "" { raw, _ = base64.StdEncoding.DecodeString(enc) }
> ```
> Чтение файла по argv-пути оставьте фоллбэком — старый хост ещё может передать путь.
>
> **3. Слушающим SOCKS5-сокетом владеет хост.** Он его создаёт и передаёт готовым: Desktop-Unix —
> наследованием fd (номер в `ANTINET_LISTEN_FD`), Android — тем же номером параметром `listenFd`.
> Даёт три вещи: порт известен хосту сразу и авторитетно; сокет **переживает смерть и подмену
> модуля** (входящие копятся в backlog ядра, sing-box не получает `ECONNREFUSED`); исчезает гонка
> ре-бинда того же порта.
> ```go
> ln, err := net.FileListener(os.NewFile(uintptr(fd), "socks"))
> ```
> ⚠ Если fd передан — **фоллбэка на `net.Listen` быть не должно**: тот же порт держит хост,
> повторный bind гарантированно даст `EADDRINUSE`, и хост увидит бесконечный crash-loop вместо
> честного провала. **Windows** — исключение: передать сокет там нечем (проверено живьём,
> `net.FileListener` отвергает и унаследованный handle, и `WSADuplicateSocket`-блоб), поэтому туда
> приезжает только `LISTEN_PORT`, и модуль биндит сам.
>
> ⛔ **Усыновление одноразовое — листенер живёт столько же, сколько процесс.** `os.NewFile`
> забирает владение дескриптором, `net.FileListener` его дуплицирует, и оригинал после этого
> закрывается: второй `FileListener` на то же число обречён на `invalid argument`. Поэтому
> усыновляйте один раз, держите `net.Listener` в переменной уровня процесса и **не закрывайте его**
> при внутренних перезапусках (смена сети, переподключение сессии) — им принадлежит только
> обработчик соединений, а не сам сокет. Accept-петля тоже одна: две петли на одном листенере
> растащат соединения, и старая отдаст их уже мёртвой сессии.
>
> Живой инцидент 2026-09-05 (masterdns/stormdns, `handoverMode: signal`): помощник усыновлял
> заново на каждом перезапуске сессии и падал с
> `усыновление listenFd=137: file file+net antinet-socks: invalid argument` → `fatal`. Первый
> перезапуск проходил, **каждый второй убивал модуль** — триггером обычно была смена сети, но
> причина к ней отношения не имела.
>
> **4. Готовность модуль отмечает файлом `ready`.** Порт хост знает сам — он его и выдал, — так что
> от модуля нужен только сигнал «поднялся». Пишите рядом и `socks.port` с номером порта: он копеечен
> и понятен хостам, которые читают его вместо `ready`.
>
> **5. Контракт восстановления состояния.** Хост даёт две вещи и не интерпретирует ваше состояние.
>
> `START_REASON` в конфиге — почему модуль запустили:
> * `cold` — состояния нет либо пользователь его сбросил;
> * `resume` — модуль работал, процесса нет. **Смерть процесса и force-stop клиента строго
>   равноценны**: хост не различает причины смерти и отдельного значения для них не заводит;
> * `handover` — то же плюс **сеть сменилась**, чего модуль сам знать не может.
>
> `MODULE_STATE` — ваш же непрозрачный блоб прошлой сессии. Отдаёте строкой
> `STATE_SAVE|<base64>` в stdout, получаете обратно ключом `MODULE_STATE=` при следующем старте.
> Хост его не разбирает и не толкует: формат, срок годности и валидность — целиком ваши.
>
> ⚠ **Блоб живёт в памяти хоста, а не на диске** — намеренно: в нём обычно секреты (у qWDTT это
> TURN-креды), а `data/`-дерево на Desktop world-readable. Переживает смерть модуля, хендовер,
> обновление модуля и ручную остановку туннеля (процесс хоста жив); не переживает полный
> force-stop приложения — там будет честный `cold`. Размен осознанный.
>
> Что с этим делать — решает модуль, и все три ответа легитимны:
> * **полное восстановление** (qWDTT): кэширует TURN-креды и на `resume` пропускает всю
>   VK-цепочку включая капчу;
> * **time-boxed** (echo, образец): подтверждение пользователя годно 15 минут, дальше спрашивает снова;
> * **всегда cold** (MasterDNS): осознанно ничего не переиспользует — переиспользование резолверов
>   без повторного пробинга давало 88 подряд отказов DNS, это задокументированный негативный пример.
>
> Отказывайте при любой неоднозначности: нет блоба, битый base64 или JSON, сменилась ссылка, истёк
> срок, пришёл `cold`. Переспросить или получить заново дешевле, чем работать на протухшем состоянии.

Go-бинарь (Desktop) / `c-shared`-библиотека (Android). На Desktop AntiNet форкает его с
**аргументами**:

```
myhelper  <configPath>  <resolversPath>  <profileDir>  <protectPath>
```
| arg | смысл |
|---|---|
| `configPath` | фоллбэк-путь к `KEY=VALUE` и `LINK`; реальное содержимое приезжает в `ANTINET_MODULE_CONFIG` |
| `resolversPath` | дополнительный файл (состояние, резолверы; модуль волен использовать его или нет). Не путать с `DNS_SERVERS=` (см. ниже): этот файл несёт протокол-специфичное содержимое, а `DNS_SERVERS=` — реальные резолверы физической сети |
| `profileDir` | writable-каталог helper'а (state, логи) |
| `protectPath` | UNIX-сокет protect-сервиса AntiNet (см. ниже) |

**Формат конфига одинаков на обеих платформах (Android и Desktop): пары `KEY=VALUE` и сырая `LINK`.**
Хост даёт per-session SOCKS5-креды и порт плюс **сырую** непрозрачную ссылку; helper декодирует её
сам, тем же парсером, что `summarize` и `normalize`:
```
LISTEN_PORT=<socksPort, 0=эфемерный>
SOCKS_USER=<user>
SOCKS_PASS=<pass>
LINK=<сырая myproto://… ссылка как есть>
```
- Helper читает `LISTEN_PORT`/`SOCKS_USER`/`SOCKS_PASS` → слушает SOCKS5 с этими кредами (эфемерный порт
  `0` → выбирает сам и пишет в `socks.port`), декодит `LINK` своим парсером → собирает свой data-plane.
- Формат одинаков на обеих платформах, и glue-слоя на стороне хоста нет: один Go-самодекод в самом
  helper'е обслуживает и Android, и Desktop.
- Референсы: `examples/moduleecho` (echo://-passthrough), `(репозиторий AntiNet) examples/moduleqwdtt/native/qwdtt/helper.go::
  parseConfig` (KEY=VALUE → `summarizeQwdtt`/`normalizeQwdtt` тем же декодером),
  `(репозиторий AntiNet) examples/modulemasterdns/native/MasterDnsVPN/cmd/helper/config.go` (`parseConfig` →
  `decodeStormDns`/`buildStormDnsConfig`/`withSocksAuth`).

**`DNS_SERVERS=<ip[,ip...]>` (опционально, generic, не путать с `resolversPath`)** — реальные
физические DNS-серверы сети: тот же примитив, которым резолвит остальной клиент (Android
`ConnectivityManager.getLinkProperties(physicalNet)?.dnsServers`, Desktop
`PhysicalAdapter.NativePhysicalDnsServers`). Позволяет любому модулю резолвить свои dial-таргеты
(host у TCP CONNECT и доменные таргеты у UDP ASSOCIATE, п. 6 ниже) protected off-tunnel вместо ухода
в TUN-перехват (см. п. 2). Формат — голые IP через запятую (`ip:53` подразумевается) либо явные
`ip:port`; разбирайте обычным `strings.Split(csv, ",")`, CSV-кавычек там не бывает. **Пусто** —
детект на хосте не удался, и модуль сам решает, деградировать ли (echo деградирует: фоллбэк на
`net.DefaultResolver.LookupHost`, старое поведение). Не путать с `resolversPath` выше: тот несёт
протокол-специфичное содержимое — у MasterDNS это список DNS-туннельных резолверов из ссылки
подписки, с реальной сетью никак не связанный.

**`DEVICE_ID=<hwid>` (опционально, generic)** — стабильная идентичность **устройства**, одна на всё
приложение: Android `SubscriptionUpdateManager.computeNativeHwid` (MediaDrm-ID, иначе ANDROID_ID, и
SHA-256 поверх), Desktop `ComputeNativeHwid` — тот же источник, которым HWID уходит в заголовки
подписок. Нужен модулю, чей сервер привязывает доступ к устройству и лимитирует их число.

⚠ **Ключевое слово — «устройства», а не «конфига».** Модуль, выводящий такой id из своих же полей
(пароль плюс адрес сервера), получит разный id на каждый конфиг: одно устройство займёт у сервера
столько слотов, сколько у пользователя конфигов, а доступ, привязанный другим клиентом того же
устройства, останется недостижим. Именно на этом ключ и появился — сервер qWDTT отвечал
`DENIED:device_mismatch` («пароль привязан к другому устройству»).

**Пользоваться ключом — право, а не обязанность.** Модуль вправе иметь свою схему идентичности и
`DEVICE_ID` игнорировать (qWDTT так и делает намеренно). **Пусто** (источник недоступен) — ключа
нет вовсе.

**`APP_LANG=<ru|en>` (опционально, generic)** — эффективный язык AntiNet: Android
`LocaleHelper.effectiveLanguage(ctx)`, Desktop `i18n.EffectiveLang` — явный выбор пользователя в
настройках приложения, иначе локаль ОС. Это **не сырая системная локаль** модуля: модуль обязан
ориентироваться именно на этот ключ (§2.9 «Локализацию текста решает модуль, хост даёт только
`APP_LANG=`»), иначе его текст разойдётся с языком, который пользователь реально видит в AntiNet.
Референс — `examples/moduleecho/native/echo/cmd/helper/main.go::demoStringsFor`.

**Helper обязан:**
1. **Слушать SOCKS5** с per-session кредами из конфига — на сокете, который передал хост
   (`net.FileListener` на переданный fd или `listenFd`, **без** фоллбэка на свой `net.Listen`, см.
   врезку выше), либо, если это Windows и сокет передать нечем, забиндить самому именно заданный
   `LISTEN_PORT`. Готовность отмечается атомарным маркером `<profileDir>/ready` — AntiNet поллит его
   до 95 секунд и считает helper готовым по его появлению. `socks.port` с одним числом можно писать
   тоже: это копеечно и нужно для совместимости со старым хостом, но основным сигналом уже не
   является.
2. **Протектить исходящие сокеты off-TUN**: каждый исходящий fd отправить через **`SCM_RIGHTS`** на
   `protectPath`, и protect-сервис AntiNet поставит bypass-метку. Без этого сокеты helper'а текут в
   TUN и получается петля. Референс, самодостаточный и пригодный для копирования:
   `net.Dialer{Control: protectControl(protectPath)}` плюс `protectViaService`/`protectOnce` в
   `examples/moduleecho/native/echo/cmd/helper/main.go`.

   **Протект сокета не покрывает DNS-резолв ваших же dial-таргетов.** Обычный
   `net.DefaultResolver.LookupHost` под Husi-pattern (наш UID включён в TUN) уходит в TUN, попадает
   под DNS-hijack и дальше в чужой пайплайн sing-box (`dns-remote`, direct, local): не сломано, но
   непредсказуемо медленно и зависит от состояния активного каскада. Хост даёт
   `DNS_SERVERS=<ip[,ip...]>` (см. ниже) именно для protected off-tunnel резолва — используйте его
   для своих dial-целей (host у TCP CONNECT и доменные таргеты у UDP ASSOCIATE, если реализуете
   п. 6). Это **канон `shared/dns/`** (`newProtectedResolver`/`LookupHost`: TTL-кэш, single-flight и
   прямой UDP-запрос A/AAAA через ваш же `dialControl`), инжектируемый при `"dnsResolver": true` —
   своей копии писать не надо (§4).
3. `unix.Prctl(PR_SET_PDEATHSIG, SIGKILL)` — «умереть вместе с родителем». В референс-модулях это
   канон `dieWithParent` (`shared/lifecycle`).

   Где именно он срабатывает:
   - **Desktop-Linux** — helper форкнутый ребёнок бэкенда, PDEATHSIG снимает орфана мгновенно
     (`lifecycle_dieparent_linux.go`, тег `//go:build linux && !android` обязателен: GOOS=android
     удовлетворяет и тегу `linux`);
   - **Android** — родитель слот-процесса zygote и не умирает, поэтому вызов безвреден, но орфана
     не ловит. Защита здесь — самореап слота в `ModuleHostService.onDestroy`;
   - **Windows/darwin** — аналога PDEATHSIG нет (`lifecycle_dieparent_nonlinux.go`, no-op),
     единственная защита — стартовый свип хоста (`taskkill /F /IM`). Закрыть нечем, кроме
     job-объектов Windows, а они меняют модель запуска целиком.

   Стартовый свип хоста (`CleanupOrphanHelpers`, `pkill -9 -f modules/<scheme>/<helper>`) работает
   на всех ОС и не снимается даже там, где `PDEATHSIG` есть: это страховка для helper'ов, переживших
   пересборку или смену версии модуля.
4. **Не виснуть на pipe**: AntiNet редиректит stdout в файл. Пишите логи, но не рассчитывайте, что
   кто-то дренирует pipe — недренируемый pipe вешает data-plane.
5. **Переживать relaunch на том же порту**: на смене сети AntiNet (при `handoverMode: "restart"`, а
   также когда событие `"signal"`-модулю не доставлено) убивает и заново поднимает helper с тем же
   стабильным `LISTEN_PORT`, и helper должен снова поднять на нём SOCKS5. У `"signal"`-модуля тот же
   порт обязан пережить его собственный in-place self-heal (§2.8, п. 3).
6. **Опционально, если ваш транспорт несёт произвольный UDP, — поддержать SOCKS5 UDP ASSOCIATE
   (CMD 0x03).** Нужно, когда ваш модуль стоит основой каскада, а второй хоп — UDP-протокол
   (hysteria2, tuic, wireguard, QUIC поверх UDP): sing-box дозванивается до сервера каскада по UDP
   через ваш SOCKS5, то есть командой 0x03. Ответ `0x07 (command not supported)` даёт
   `socks5: request rejected, code=7`, и UDP-каскад умирает (обычный CONNECT-трафик и TCP-каскады при
   этом не затронуты). Реализуйте UDP ASSOCIATE только если транспорт реально несёт произвольный UDP:
   **qWDTT — да** (relay через netstack), **echo — да** (демонстрирует голый UDP-relay без своего
   туннеля: плоский passthrough к отрезолвленному таргету через тот же `protectControl`, что и TCP);
   **DNS-туннель MasterDNS — нет** by design: он несёт только DNS-UDP на порт 53, UDP-каскады через
   него невозможны, его socks принимает ASSOCIATE, но дропает всё, что не 53. CONNECT-only
   socks (без UDP ASSOCIATE) — валиден для TCP-only сценариев.
   ⛔ **CONNECT-only модуль обязан объявить `"socks5Udp": false`** (§2.12). Отвечать `0x07` по факту
   запроса недостаточно: до модуля доходит не только каскад, но и обычный QUIC приложений, и каждый
   такой отказ ядро засчитывает как отказ дозвона — замер на устройстве: `fails=9/3`,
   `FIRE tag=proxy-primary reason=dial failures: socks5: request rejected, code=7`, после чего хост
   дёргает исправный модуль щадящим переподключением. С объявленным `false` хост выставляет
   `"network": "tcp"` у вашего socks-аутбаунда, и UDP отбивается роутером до дозвона — счётчик
   здоровья его не видит вовсе. Молчание равносильно `true` (обратная совместимость).

   **Весь протокол SOCKS5 — канонический shared-пакет, вручную его копировать не надо**:
   `shared/socks5/socks5shared.go` (рукопожатие, авторизация, разбор запроса, accept-петля, реле,
   UDP ASSOCIATE) инжектируется `build.py` в main-пакет вашего helper'а при `"socks5": true` в
   `module.json` — тем же механизмом, что `shared/protect` и `shared/offtun`. Ваше дело — транспорт:
   реализовать `socksUDPTransport` (`LookupHost` и `DialUDPTarget`) и свой CONNECT-дозвон. Референсы:
   `qwdtt/socks5.go::cachedResolver` (резолв и дозвон через свой `tnet` — цель уже внутри
   установленного туннеля) и `moduleecho/cmd/helper/main.go::echoUDPTransport` (через свой
   off-tunnel `protectedResolver` и protected-dialer — цель снаружи, п. 2 выше). Что значит «резолв»,
   решает ваш резолвер; канон про его смысл не знает.
7. **Self-heal: транзиентные сбои ретраить внутри процесса, выходить через `os.Exit` только на
   по-настоящему фатальное и никогда не зомбировать.** Сетевой или резолверный сбой на старте — нет
   маршрута, ноль рабочих резолверов в окне после хендовера или сброса carrier-NAT, когда protect ещё
   не на новой сети — транзиентный: ретрайте внутри процесса, как это делает `Run`-цикл MasterDNS на
   `ErrNoWorkingDNS` (backoff 5 с и снова, без выхода), потому что то же условие уйдёт через секунды.
   На по-настоящему фатальное — битый конфиг, неустранимая runtime-ошибка — зовите **`os.Exit`**, а не
   виснете на `select{}` или в простое с мёртвым data-plane: иначе процесс остаётся зомби без маркера
   `ready`, AntiNet ждёт `READY_TIMEOUT` около 95 секунд и сообщает «модуль не запустился». Чистый
   выход, наоборот, даёт мгновенный relaunch от death-watchdog. **Антипаттерн, встреченный живьём в
   StormDNS:** счесть транзиентный «ноль рабочих резолверов» фатальным и выйти или зомбировать — тогда
   один блип сети после хендовера убивает DNS-туннель до ручного реконнекта. AntiNet со своей стороны
   на крэш-петле не сдаётся навсегда (backoff и ре-арм, §2.10), но это подстраховка: helper обязан сам
   не превращать транзиент в смерть или зомби.

**Что AntiNet делает со своей стороны автоматически, без правок в вашем коде:** сразу после форка
хост снижает `/proc/<childPid>/oom_score_adj` вашего helper'а до `-1000` — это минимум ядра, уровень
`init`, «никогда не убивать». Helper'у для этого делать ничего не нужно: хост накладывает это на
любой модуль, включая сторонние, чей Go-код нам недоступен. Kernel-level LMK (low-memory-killer)
закрывается безусловно.

**Панацеей это не является**: вендорские battery- и task-killer'ы (Transsion, MIUI, ColorOS, EMUI и
прочие) часто работают по своей эвристике, отдельной от `lmkd`, и могут это поле игнорировать. Против
них помогает только согласие пользователя в «защищённых приложениях» или «автозапуске» конкретной
прошивки — это вне контроля кода. Если ваш helper дополнительно пишет собственный
`/proc/self/oom_score_adj=-1000` на старте (`protectFromOomKill()` из канона `shared/lifecycle/`), это
defense-in-depth: закрывает более раннее окно между форком и первой строчкой `main()`. Требованием
такая запись не является — хост защищает helper и без неё.

### 2.4. Сборочных требований к модулю нет

Модуль — не приложение, поэтому Gradle, Android SDK и AGP ему не нужны вовсе: всё собирается
`python build.py` + Go + NDK (§5).

#### Доп. нативные библиотеки рядом с helper'ом

Helper — не обязательно весь модуль: его data-plane может жить в библиотеке на другом языке,
которую helper грузит `dlopen`'ом (у csqtt это rust-движок `libcsqtt_engine.so`). Каталог модуля
на устройстве принимает такие файлы: он распаковывается из бандла **как есть**, целиком.

⚠ **Такая библиотека платформенная и архитектурная — ровно как helper.** Под Android их столько
же, сколько ABI, а на desktop у файла меняется даже имя: `libmyengine.so` на Linux,
`libmyengine.dylib` на macOS, `myengine.dll` на Windows — без префикса `lib`. Поэтому объявление
идёт **по целям**, а не по платформам.

Объявляются они в секции `build`:

```jsonc
"nativeLibs": {
  // Ключ секции — цель сборки: то же написание, что у каталога в `dist/`, с отброшенным хвостом.
  "android": { "libmyengine.so": "native/engine/dist/android/{abi}/libmyengine.so" },  // все ABI разом
  "android/x86_64": { "libmyengine.so": "native/engine/dist/emulator/libmyengine.so" }, // уточнение под один ABI
  "desktop": { "libmyengine{dlext}": "native/engine/dist/{os}_{arch}/libmyengine{dlext}" },
  "desktop/windows": { "myengine.dll": "native/engine/dist/windows_{arch}/myengine.dll" },
  "desktop/darwin_arm64": { "libmyengine.dylib": "native/engine/dist/mac-m1/libmyengine.dylib" },
  "hint": "собрать движок: pwsh -File native/engine/build.ps1"
}
```

Внутри секции ключ — **имя файла рядом с helper'ом**, значение — где лежит собранный результат
(путь от каталога модуля). `hint` — одна строка, которую сборщик покажет, когда файла не окажется.

Подстановки работают **и в имени, и в пути**: `{abi}` (Android), `{os}` / `{arch}` (desktop),
`{dlext}` — расширение разделяемой библиотеки целевой ОС (`.so` / `.dll` / `.dylib`).

| цель | какие секции смотрит сборщик, в этом порядке |
|---|---|
| Android, ABI `arm64-v8a` | `android/arm64-v8a` → `android` |
| Desktop, `windows_amd64` | `desktop/windows_amd64` → `desktop/windows` → `desktop` |

⛔ **Побеждает первая объявленная секция — уровни не складываются.** Секция перечисляет файлы
цели целиком, поэтому `desktop/windows` не «дополняет» `desktop`, а заменяет его: иначе под
Windows уехал бы файл, собранный для другой ОС. Ключ, которого в этой таблице нет (`windows`
вместо `desktop/windows`, опечатка в ABI), — **отказ сборки**, а не молчание: ненайденная секция
выглядела бы как «библиотек не объявлено», и цель собралась бы без движка.

Когда один шаблон честно покрывает все цели — хватает одной строки с `{dlext}`; когда нет
(у csqtt rust-движок лежит в cargo-раскладке `target/<rust-triple>/release/`, а rust-триплет из
`{os}`/`{arch}` не выводится) — пишутся секции под каждую цель, и это нормальный вид объявления.

⛔ **Сборщик эти библиотеки не собирает — он их только довозит и проверяет.** Тулчейн у них свой
(cargo, cmake, что угодно), а исполнять команду сборки из чужого дескриптора значит запускать
чужой код на машине того, кто собирает. Соберите их своим скриптом и объявьте, где лежит
результат.

Что сборщик делает взамен:

| когда | что |
|---|---|
| `--os <цель>` | копирует объявленные файлы в `dist/<цель>/` рядом с helper'ом; файла нет — **сборка отказывает** и печатает `hint` |
| `--bundle` | не собирает релиз, если объявленного файла нет в каталоге цели — той же проверкой, что и подпись `bundleTarget` |
| `--doctor --module <мод>` | проходит по целям поимённо (каждый ABI, каждая desktop-ОС) и говорит, где файл лежит, а где его нет; не хватает хоть одного — **выходит с ошибкой** |

⚠ **Почему отказ, а не предупреждение.** Каталог цели уезжает в бандл целиком, и неполный каталог
даёт модуль, который ставится без единой жалобы, а падает уже на устройстве: helper стартует,
зовёт `dlopen` и не находит движок. Живой случай csqtt: сборка отрапортовала успехом, а на
телефоне — `libcsqtt_engine.so not found next to helper`, и увидеть это можно было только в логе
модуля.

### 2.5. Карточка «Модули» + обновления (опционально)

AntiNet показывает установленные модули в **Настройки → Модули** (имя · версия · описание · ссылка
+ авто-проверка обновлений). Всё берётся из `module.json` (§2.1); без этих ключей модуль работает,
просто карточка беднее:

```jsonc
{
  "name": "My Protocol",
  "description": "Что делает модуль",
  "homepage": "https://github.com/owner/repo",
  "version": "1.3.0",       // единственная версия: и показ, и сравнение
  "updateUrl": "https://raw.githubusercontent.com/owner/repo/main/antinet-module.json"
}
```
- `name` — имя в карточке «Модули» **и внешний лейбл протокола в списке конфигов** (chip). Нет
  имени — карточка возьмёт имя каталога модуля, а chip покажет схему заглавными (`qwdtt` → «QWDTT»).
  **Держите его коротким и человекочитаемым** («qWDTT», «StormDNS»): это и есть отображаемое имя
  протокола, по аналогии с `ss://` → «Shadowsocks», а не «SS». Подробности и расшифровку кладите в
  `description`, а не в `name`. `description` — что делает модуль; `homepage` — человеческая
  страница или репозиторий (кликабельная ссылка); `updateUrl` — адрес JSON-манифеста версии для
  авто-проверки (без него авто-проверки нет, карточка просто показывает версию и homepage).
- **`version` — единственная версия модуля: и показывается, и сравнивается.** Отдельного монотонного
  `versionCode` нет и заводить его не надо: две версии на один артефакт неизбежно разъезжаются, а
  правите вы всё равно только человекочитаемую.
  **На каждый релиз поднимайте `version`**, иначе авто-проверка не увидит обновление.
  Сравнение идёт посегментно числами (`1.3.10` > `1.3.7` > `1.3.7-beta`), разделителем считается
  любой не-цифровой символ, недостающие сегменты равны нулю (`1.4` > `1.3.9`). Схема
  версионирования ваша, лишь бы числа росли.

**Много-протокольный модуль (несколько `schemes`) — опциональный `names`:**
```jsonc
{ "schemes": ["protoa", "protob"], "names": ["ProtoA", "ProtoB"] }
```
- `names` — список chip-имён, параллельный `schemes`, индекс в индекс: `protoa` → «ProtoA»,
  `protob` → «ProtoB». Один helper обслуживает все схемы; карточка «Модули» одна на модуль (имя из
  `name`), а chip в списке конфигов свой у каждого протокола (из `names`). Если `names` короче
  `schemes` или отсутствует, недостающие схемы берут одиночный `name`, а если нет и его — схему
  заглавными. Одно-протокольному модулю `names` не нужен.

**JSON-манифест версии** (цель `updateUrl`) — крошечный файл рядом с релизом, например на GitHub raw.
Форма одинакова для обеих платформ: одна `version` и карта «архитектура → URL бандла» на каждый backend.
```json
{ "version": "1.3.0",
  "android": {
    "arm64-v8a":   "https://github.com/owner/repo/releases/download/v1.3.0/mymod-android-arm64-v8a.zip",
    "armeabi-v7a": "https://github.com/owner/repo/releases/download/v1.3.0/mymod-android-armeabi-v7a.zip"
  },
  "desktop": {
    "windows_amd64": "https://github.com/owner/repo/releases/download/v1.3.0/mymod-windows_amd64.zip",
    "linux_amd64":   "https://github.com/owner/repo/releases/download/v1.3.0/mymod-linux_amd64.zip"
  },
  "changelog": "что нового" }
```
| поле | обяз. | смысл |
|---|---|---|
| `version` | да | строка («1.3.0»); AntiNet сравнивает посегментно-числами с установленной → «доступно обновление» |
| `android` | для Android | `{ "<abi>": "<bundle-url>" }` — плоский ZIP каталога `dist/android/<abi>/` |
| `desktop` | для Desktop | `{ "<os>_<arch>": "<bundle-url>" }` — плоский ZIP каталога `dist/desktop/<os>_<arch>/` |
| `changelog` | нет | текст «что нового» |

Обязательным для каждой платформы считается свой ключ: манифест без бандла под арку текущего
устройства этой платформой отвергается целиком (нечего ставить). Модуль без `android` — desktop-only и
наоборот; это легитимно, просто на второй платформе авто-обновление становится no-op.

Оба ZIP'а **плоские**: `module.json` и артефакт лежат в корне архива, без подпапки — ровно то, что
распаковывается в каталог модуля. Собирает их `python build.py --bundle --module <X>`, он же генерит
скелет манифеста с плейсхолдерами URL.

В бандл попадает **весь каталог цели**, а не только эти два файла: если модуль несёт доп. нативные
библиотеки (§2.4) или per-OS установщик, они лежат рядом и доезжают до устройства тем же
распаковыванием. Поэтому каталог цели и обязан быть полным — `--bundle` отказывается собирать
релиз, если объявленного файла в нём нет.

**`bundleTarget` — подпись арки внутри бандла.** В `module.json` каждого бандла сборщик пишет ключ,
под которым этот бандл обязан лежать в манифесте: `arm64-v8a` для Android, `linux_amd64` для
Desktop. Автор его не пишет и не правит — поле генерируется (`build.py::_flat_descriptor_base`) из
цели сборки, поэтому разойтись с содержимым каталога ему нечем.

Зачем оно, если арка и так видна в самом артефакте:
- **публикация**: `--bundle` отказывается собирать релиз, если подпись хоть одного бандла не
  совпала с его ключом, и отказывается до записи первого архива — перепутанный бандл иначе
  обнаружился бы у пользователя, чей клиент скачал «своё» обновление и откатился;
- **UX на устройстве**: хост пишет в пользовательский лог, что принесли и что нужно
  («бандл собран под arm64-v8a, а устройству нужен armeabi-v7a»), вместо общей фразы.

⛔ **Это не пропуск на установку.** Годность решает сам артефакт: Android читает ELF-заголовок
`.so`, Desktop — сигнатуру PE/ELF/Mach-O, и при расхождении установка откатывается независимо от
того, что написано в подписи. Подпись — заявление, артефакт — факт; когда они спорят, прав
артефакт. Бандл без подписи (собран старым `build.py`) устанавливается как раньше — по артефакту,
а вот опубликовать его новый `--bundle` откажется, потребовав пересборки.

**Поток обновления — одинаковый на обеих платформах, полностью автоматический, SILENT.** Модуль — это
каталог (`module.json` + артефакт) в приватном хранилище клиента, а не приложение, поэтому
OS-гейткипера установки нет ни там, ни там:
1. Авто-апдейтер (по интервалу) или ручная кнопка «Скачать обновление»: GET манифест → новее? есть
   бандл под нашу арку? → **скачать** (через туннель/direct по `fetchMode`, как геофайлы) → **поставить
   молча**: остановить live-helper модуля → распаковать → (Desktop) `chmod +x` helper'а / (Android)
   пометить `.so` read-only, как требует Dynamic Code Loading → re-discover → **relaunch** прежде-живого
   helper'а. Браузер и системный установщик не задействуются нигде.
2. Распаковка **rollback-safe целиком**: старый каталог паркуется рядом и возвращается на место, если
   что-то пошло не так — модуль не остаётся с несовместимой парой «новый артефакт + старый дескриптор».
3. **Состояние сессии обновление переживает** — профиль/креды живут отдельно от каталога установки
   (§2.3, callout «Контракт восстановления состояния»), поэтому после подмены модуль стартует с
   `START_REASON=resume`, а не заново.
4. Если бандла под текущую арку нет — ставить нечего: карточка показывает «Доступно vX», но применить
   не сможет (пользователь может открыть «Страница»).
5. Тумблер «Автообновление модулей» в карточке Настройки → Модули (default OFF) + интервал (дни) +
   `fetchMode`. Через туннель качается, когда direct заблокирован провайдером (тот же механизм, что гео).

> **Почему JSON-манифест, а не GitHub Releases API:** парсинг `tag_name` привязывает к GitHub и его
> rate-limit'у; манифест host-agnostic и проще. **Почему одна `version`, а не пара
> `versionCode`+`versionName`:** вторая версия существует только чтобы её забыли поднять — правите вы
> всё равно человекочитаемую, а сравнение посегментно-числами и так однозначно.

> **Куда заливать (два разных требования к URL, не путать):** ZIP'ы — на что угодно со стабильным
> file-hosting'ом (GitHub Releases-ассет, S3/R2, свой VPS+nginx); их URL **меняется** на каждый релиз —
> это нормально, манифест как раз и существует чтобы указывать на актуальный. А вот URL самого
> манифеста — тот, что разово прописывается в `updateUrl` и живёт в `module.json` уже установленных
> у пользователей копий — обязан быть **стабильным** (never change), иначе `updateUrl` из уже распространённых
> версий будет указывать в прошлое. GitHub Release-ассет для этого не годится (у каждого релиза свой
> immutable URL) — берётся URL файла на ветке (`raw.githubusercontent.com/<owner>/<repo>/main/
> antinet-module.json`), который автор просто перезаписывает при каждом релизе, коммитя новую версию
> в тот же путь. Тот же принцип на любом другом хостинге: манифест — по адресу, который сам не
> меняется, ZIP'ы — по адресам, которые меняются на каждый релиз.

> **`updateUrl` попадает в `module.json` до сборки бандлов, а не после заливки.** Дескриптор едет
> внутри каждого ZIP'а (плоская форма, см. ниже), поэтому адрес, вписанный после публикации бандлов,
> не существует ни для одного пользователя: у установленной копии нет ни авто-проверки, ни рабочего
> «Поделиться модулем» — ссылка уходит без `m`, и получателю ставить неоткуда. Пустой `updateUrl`
> сборщик в дескриптор не пишет вовсе (`build.py` пишет ключ только непустым), так что по
> установленной копии «адреса нет» и «адрес забыли вписать» неотличимы. Отсюда порядок: дескриптор →
> `--bundle` → заливка; смена адреса = пересборка и перезаливка бандлов. Оверрайд адреса в карточке
> «Модули» (`moduleUpdateUrl`) лечит уже установленную копию — и её ссылку «Поделиться» тоже, хост
> подставляет туда эффективный адрес, — но это правка на стороне пользователя, а не замена шага автора.

**Install-ссылка `antinet://import?module=<b64url-json>` (момент 4)** — как распространить модуль, чтобы
пользователь поставил его в один тап. Когда AntiNet импортирует такую ссылку (вставка / QR / deep-link) и
видит, что объявленной `scheme` не соответствует ни один установленный модуль → показывает диалог
«Установить модуль «Имя»?» → «Скачать» → берёт из манифеста (`m`) бандл под свою арку → ставит **молча**,
тем же путём, что обновление. JSON (компактные ключи, base64url-no-pad):
`{"s":"<scheme>","n":"<имя>","m":"<updateUrl-манифест>","h":"<homepage>"}` — `s`+`n` обязательны, `m`
нужен для установки (без него ставить неоткуда — предложим открыть `h`). Можно несколько `&module=`
(модуль на несколько схем — ставится один раз). Уже установленные scheme в очередь не попадают (no-op).
Совмещается с импортом подписки: `antinet://import?url=<sub>&module=<b64>` ставит модуль и импортирует
подписку. Сгенерировать ссылку — Настройки → Модули → «Поделиться модулем». АнтиНет формат ссылки не
навязывает автору — модуль может опубликовать её сам по этой схеме.
> Ключ `"a"` в схеме ссылки объявлять не надо: Android его игнорирует, Desktop использует лишь как
> последний вариант «что открыть в браузере», если ни `m`, ни `h` не дали ничего.

### 2.6. Импорт не-link форм (JSON-конфиг из файла, base64) — опционально

По умолчанию AntiNet импортирует конфиг модуля как `scheme://`-ссылку (вставка/QR — её ловит реестр
схем). Если ваш формат живёт также как **JSON / base64** (без `scheme://`-обёртки — напр. файл-конфиг),
реализуйте сабкоманду **`normalize`** в helper'е (§2.2):

```
helper normalize <raw>    →  stdout: канонический scheme://-link  (или пусто)
```
- Получает произвольный вставленный текст (содержимое файла / QR). Узнал свой формат → печатает канонический
  `scheme://`-link (тот же, что потом парсят `summarize` и самодекод коннект-пути); чужой/уже-link/не узнал
  → печатает пусто (`exit 0`).
- AntiNet при импорте текста, который сам не классифицировал, форкает `helper normalize <raw>` у всех
  установленных модулей; первый непустой link → идёт в обычный `parse`. Сабкоманды нет (helper не понял) →
  модуль пропускается.

Так файл `.qwdtt` с сырым JSON `{…}` (или его base64) «просто вставляется» в AntiNet — helper превращает
его в свой `scheme://`-link. Пример — `(репозиторий AntiNet) examples/moduleqwdtt/native/qwdtt/helper.go::normalizeQwdtt` (понимает
`qwdtt://` URI + JSON + base64 + alt-ключи). Однострочный `scheme://`-link работает и без этой сабкоманды.

### 2.7. Интерактивное действие по ходу коннекта (капча / логин / 2FA / подтверждение) — опционально

Если для установления соединения модулю нужно **действие пользователя в UI** (решить капчу, ввести
логин/код, подтвердить) — helper во время коннекта отправляет запрос и блокируясь ждёт результата.

> ### ⚠ UI рисует AntiNet, модуль присылает правило
>
> Payload — **декларативное правило**, которое интерпретирует и исполняет сам AntiNet;
> модуль не несёт ни строчки UI. Правило одно и то же для обеих платформ (Android рисует
> `ModuleActionActivity`, Desktop — `antinet-action`-рендерер хоста):
>
> | поле | смысл |
> |---|---|
> | `type` | `confirm` / `form` / `choice` / `display` / `webview` (по умолчанию `webview`, если задан `mode`) |
> | `mode` | `network` — перехват fetch/XHR; `navigation` — слежение за переходами |
> | `url` | что открыть; **список** кандидатов допустим (не сработало за `urlTimeoutSec` → следующий) |
> | `endpointPattern` | (network) подстрока URL интересующего ответа |
> | `bodyPattern` | (network) подстрока тела ответа — когда URL непредсказуем |
> | `jsonPath` | (network) путь извлечения; **список** альтернатив, первый найденный побеждает |
> | `requireFields` | (network) не отправляеть, пока в ответе нет всех перечисленных путей (от корня) |
> | `urlPattern` + `param` | (navigation) какой URL ловить и какой query/fragment-параметр извлечь |
> | `injectJs` | произвольный JS **от модуля** (автоклик и т.п.); хост его лишь исполняет |
>
> Объект/массив уезжает модулю как `JSON.stringify(...)`, а не `"[object Object]"` — значит
> правилом можно вытащить не только строку, но и целую структуру (напр. `{username,credential,urls}`).
> Референс живого правила: `(репозиторий AntiNet) examples/moduleqwdtt/native/qwdtt/vk_account.go` (перехват `turn_server`
> со страницы звонка VK + `injectJs`-автоклик, портированный из апстрима).
>
> **Результат приходит каналом, а не файлом** (он такой же секрет, как конфиг): Desktop — строкой
> `ACTION_RESULT|<id>|<payload>` в **stdin** helper'а, Android — тем же текстом в
> `antinet_module_event`. Файл `action_result.<id>` остаётся фоллбэком там, где канала нет.
>
> **⚠ Приватность, если правило открывает чужой сайт с логином** (как VK-режим qWDTT): такое
> действие требует живой сессии пользователя, и cookie этой сессии остаются в браузерном хранилище
> AntiNet. Это обязано быть написано в описании соответствующей настройки модуля, а не
> подразумеваться.

**Три шага:**

1. **Ничего декларировать не нужно, ни на одной платформе.** Рендерер `webview`-действий принадлежит
   хосту на обеих сторонах: Android рисует сам AntiNet (`ModuleActionActivity`, часть хоста, не
   модуля), Desktop — `antinet-action[.exe]` (лежит рядом с `antinet[.exe]`, поставляется вместе с
   клиентом), форкается для любого модуля. Правило §2.5 «модуль не пишет ни строки UI» действует на
   обеих платформах одинаково, и C-тулчейн модулю для этого не нужен.

   > ⛔ Ключи дескриптора `actionActivity` и `actionBinary` объявлять не надо. Первый игнорируется
   > (§2.1). Второй — путь для сторонних модулей, поставляющих свой webview-бинарь: хост берёт его,
   > только если своего рендерера не нашёл. Полагаться на это нельзя и незачем — и хостовый
   > рендерер, и такой модульный бинарь используют один и тот же `webview_go` с одними и теми же
   > системными зависимостями, так что там, где не поднимется первый, не поднимется и второй.

2. **helper (Go)** — когда действие реально нужно: отправить в **stdout** строку
   `ACTION_REQUIRED|<id>|<payloadB64>` и **блокируясь ждать результат**. Результат приезжает
   **каналом** (Desktop — строка `ACTION_RESULT|<id>|<payload>` в stdin, Android — тот же текст в
   `antinet_module_event`; секрет на диск не кладётся, §3), а файл `<profileDir>/action_result.<id>` —
   фоллбэк для старого хоста. Референс, обслуживающий обе формы одним ожиданием, —
   `examples/moduleecho/.../main.go::awaitActionResult` (регистрация ожидания по `id` + канал +
   параллельный поллинг файла + дедлайн). `id` — уникален (несколько
   действий подряд = разные id). `payloadB64` — base64 любых данных для вашего UI (челлендж капчи,
   промпт и так далее). Результат:
   - содержимое `"CANCELLED"` → пользователь отменил, UI нет либо истёк жёсткий потолок → **выйти**
     (`os.Exit(1)`; маркер `ready` и `socks.port` не писать, туннель не поднимать). Это
     ответственность модуля: AntiNet протокол-агностичен и `CANCELLED`
     не интерпретирует — он лишь видит, что модуль «не поднялся» (нет маркера `ready`), и трактует это как обычный
     отказ коннекта (см. «Гарантии» ниже);
   - иначе → base64-результат от Activity: декодировать, использовать (токен капчи и тому подобное) и продолжать коннект.
   ```go
   fmt.Printf("ACTION_REQUIRED|%s|%s\n", id, base64.StdEncoding.EncodeToString(challenge))
   // …поллить <profileDir>/action_result.<id> до появления…
   ```

3. **UI-действие** — рисует хост из декларативного правила (§2.7-callout выше), модулю тут делать
   нечего на обеих платформах — он лишь отправляет правило и получает готовый результат:
   - **Android** — `ModuleActionActivity` (хост) интерпретирует правило, доставляет результат каналом
     `antinet_module_event` (§3, не файлом).
   - **Desktop** — рендерер хоста (`antinet-action`, исходник `Desktop/tools/antinet-action/`)
     запускается `<payloadFile> <resultFile> <id>`: читает payload, исполняет декларативное правило
     (§2.7), пишет извлечённое значение в `<resultFile>` (base64) либо `CANCELLED`. Тот же контракт
     аргументов сохранён для легаси-модулей, ещё поставляющих собственный `actionBinary`.

**Гарантии AntiNet** (`ModuleManager` + хостовый `ModuleActionActivity`): сигнал ловится
только на **connect-пути** (пользователь присутствует; на пинге — не обслуживается, helper дождётся
таймаута → конфиг `-2`); на время действия **connect-таймаут на паузе** (пользователь может решать минуты);
**hard-cap ~5 мин** на действие (нет ответа → "CANCELLED"). **Отмена действия = отказ коннекта, а не ручной
дисконнект:** ваш helper на "CANCELLED" выходит → «не поднялся» → AntiNet трактует как обычный fail коннекта
(`markConfigDead` → retry-loop: non-pinned `-2` и переход на другой конфиг, pinned — ретрай). `wasManualDisconnect`
не ставится → **в AUTO-режиме режим не приостанавливается** (пользователь не отключал VPN, лишь отказался от действия).
AntiNet не шлёт ACTION_DISCONNECT и не интерпретирует "CANCELLED" сам (агностичность — это работа хелпера).
UI-рендеринг гарантирован хостом безусловно на обеих платформах (Android — `ModuleActionActivity`,
Desktop — `antinet-action`) — от модуля тут ничего не требуется, и сценария «нечем нарисовать
диалог» не существует.

**⚠ Кроссплатформенный вывод UI — рисует процесс-владелец дисплея, и AntiNet это разруливает сам
(модулю прозрачно).** На Android `ModuleManager` живёт в app-процессе (владеет дисплеем) → запускает Activity
напрямую (`ModuleActionActivity`, for-result). На Desktop `ModuleManager` крутится в **backend'е**:
в режиме «GUI сам себе backend» дисплей есть → форк `antinet-action` (или легаси `actionBinary`, §2.7)
локальный; но при установленной службе backend **headless** (root `--console` или служба, session 0,
не та X-сессия) — форк webview там **не отрисуется**. Поэтому AntiNet в headless-режимах **делегирует
запуск приклеенному GUI** (его X-сессия): backend по IPC сообщает GUI «нужно действие», GUI форкает
`antinet-action`/`actionBinary` у себя (дисплей есть), результат возвращает backend'у. **Автору
модуля делать ничего не нужно** — контракт (шаги 1-3) один; «где именно форкнуть webview» решает
AntiNet. Нет приклеенного GUI (чистый демон без UI) → результат `CANCELLED` (показать капчу некому).
**Антипаттерн (для актора webview-рендерера, `antinet-action`/легаси `actionBinary`)**: полагаться
на конкретный `DISPLAY`/иксы — бинарь должен просто рисовать нативный webview в том окружении, где
его запустили.

Полный рабочий пример (round-trip) — `examples/moduleecho`: helper `demoInteractiveAction` (отправка и опрос результата) +
`DemoActionActivity` (confirm-диалог); гатится настройкой `showDialog` (§2.11) — выкл → чистый passthrough
(pingable, без действия). Текст/автозакрытие диалога — тоже из настроек (`dialogText`/`autoCloseSec`,
payload = JSON). Показывает идиому «гейти ACTION_REQUIRED по своему условию» + связку с настройками модуля.

**Реальный кейс — `examples/moduleqwdtt` (ручная VK-капча при провале авто-решателя), LIVE на обеих
платформах:** helper `creds.go::requestWebViewCaptcha` отправляет `ACTION_REQUIRED|id|b64({mode,redirectUri,
sessionToken})` + поллит `action_result.<id>`; UI грузит VK-страницу капчи (`redirectUri`) в webview, пользователь
проходит челлендж, `success_token` извлекается и base64 возвращается helper'у. Android — `CaptchaActivity`
(WebView); Desktop — `antinet-action` (webview_go → WebView2/WebKitGTK/WKWebView). Когда решать авто/вручную —
настройка `captchaMode {auto,rjs,wv}` (§2.11).
> ⚠ **Токен берётся строго `data.response.success_token` из ответа `captchaNotRobot.check`** (хук `fetch`+`XHR`
> ровно на этот эндпоинт) — не скан произвольного ответа / `postMessage` / URL. Иначе VK даёт **`error_code:10`**
> (неверный токен): «свободный» скан хватал не тот `success_token`. Оба UI (Android+Desktop) используют один и
> тот же interceptor-JS (порт оригинального `ManlCaptchaActivity`).
**Webview-капча требует браузера** (VK SmartCaptcha = JS-челлендж) — на Desktop это встроенный системный
webview, форкаемый процессом-владельцем дисплея (см. правило выше).

**⚠ Нативный рантайм Desktop-webview нужен хостовому рендереру, а не модулю.**
`webview_go` использует системный webview, который на части систем не предустановлен:
| ОС | Рантайм для webview-действий | Где обычно нет |
|---|---|---|
| Windows | **Edge WebView2 Runtime** (отдельный компонент, ≠ браузер Edge) | Win10 **LTSC**, Server |
| Linux | **webkit2gtk-4.0/4.1** + gtk3 (рантайм-`.so`) | минимальные/headless образы; ⚠ Ubuntu 24.04+ несёт только 4.1 → у хоста есть парные бинари `antinet-action-webkit41/40` |
| macOS | WKWebView — **встроен**, доп. зависимостей нет | — |

Рантайм требуется `antinet-action` — бинарю хоста, поставляемому вместе с клиентом. Его отсутствие
хост детектит сам (`modulemanager.pas::BinaryHasMissingSharedLibs` + перебор
`HostActionRendererPaths`) и **называет пользователю недостающий пакет**, а не роняет действие молча.
Модулю здесь делать нечего: он не несёт ни рендерера, ни его зависимостей.

> Модуль может нести per-OS установщики `install-windows.ps1` / `install-linux.sh` /
> `install-darwin.sh` в своём корне — `build.py` копирует их в бандл `dist/desktop/<os>_<arch>/`.
> Их задача — разложить файлы модуля в `<AntiNet>/modules/<dir>/`, и только: тащить системный
> webview им незачем, он нужен клиенту и приезжает с клиентом.

**Антипаттерн (запрещён)**: молча ставить системные рантаймы за пользователя «в тестовых целях»; ронять
действие без объяснения, что нужен рантайм.

### 2.8. Реакция на хендовер (смена сети) — `handoverMode` (опционально)

Helper — **отдельный процесс**, сигнала смены дефолтной сети сам не получает; его сеть-сокеты,
привязанные к ушедшей сети (protect→SO_MARK), протухают → туннель умирает до восстановления.
Ключ дескриптора `handoverMode` (`module.json`, §2.1) выбирает, как AntiNet это лечит:

| Значение | Поведение AntiNet | Когда |
|---|---|---|
| `"restart"` (**default**) | **kill + cold-restart** helper'а на том же порту (полная пересборка сессии с нуля). | Работает для любого модуля, нулевая логика. Если у вас дорогой cold-start (логин/капча/перебор) — будет медленно (qWDTT: ~20с с капчей). |
| `"signal"` | helper **не убивается** — AntiNet шлёт ему событие с причиной (по умолчанию `handover`; канал — по платформе, ниже), затем `resetNetwork` (sing-box дропает stale-conn к helper'у). | Если модуль умеет **in-process переустановить** сеть-сокеты быстро (без cold-start). |

#### Причина события — `hostEvents`

Канал у события один, а поводов четыре, и модулю они означают разное. Строка, которую он получает,
и есть причина:

| причина | когда её шлёт хост | что она значит модулю |
|---|---|---|
| `handover` | дефолтная сеть **сменилась** (Wi-Fi↔сотовая, другая точка) — сеть есть и до, и после | сокеты привязаны к ушедшей сети → пересоздать их (контракт `"signal"` ниже) |
| `netlost` | годной дефолтной сети **не стало вовсе** | дозваниваться некуда: свернуть попытки и ждать. Ошибки этого периода — не отказ сервера |
| `netback` | сеть **появилась снова** | пробовать **немедленно**, не досиживая собственный backoff |
| `stall` | сеть на месте, но у хоста **не прошла проверка связи** через модуль | транспорт мог тихо умереть — передозвониться. Сеть не менялась, писать пользователю «сменилась сеть» здесь неправда |
| `dns=<ip[,ip...]>` | физические DNS сети — **перед** `handover`/`netback`/`stall` | ничего, если резолвер канонный: он подписан на список сам. Свой резолвер — взять их вместо прежних и сбросить кэш |

`netlost`/`netback` приходят от того же владельца дефолтной сети, что и `handover`, и **ничего не
перезапускают**: хост сообщает факт, решение за модулем. `stall` — единственная причина не от ОС:
её шлёт health-путь хоста как щадящую первую ступень, до перезапуска процесса.

⛔ **`dns=` — единственная причина с полезной нагрузкой, и она обязательна для любого модуля,
который резолвит свои dial-таргеты сам** (канон `shared/dns`, ключ конфига `DNS_SERVERS`).

Причина в том, что `DNS_SERVERS` приходит ровно один раз — с конфигом при запуске процесса — и
описывает сеть, активную в тот момент. После смены сети прежние резолверы недостижимы: запрос
уходит и не возвращается, и SOCKS5 отвечает `0x04 host unreachable` на каждый CONNECT. Транспорт
модуля при этом жив, поэтому ни `handover`, ни собственный re-dial этого не лечат — до появления
причины помогал только перезапуск процесса, который и переподставлял список.

Живой замер (OpenFlux, 2026-09-17): процесс прожил ~12 часов через несколько смен сети, все
резолвы били в DNS первой сети (`dns: read 8.8.4.4:53 … i/o timeout`), и каждый эпизод пользователь лечил
ручным перезапуском модуля.

Правила причины:

- приходит **перед** причиной, по которой модуль будет переустанавливать связь: иначе его re-dial
  успеет отрезолвить свой хост прежними, то есть заведомо нерабочими, резолверами;
- через подмену на `handover` **не проходит** (в отличие от остальных): таблица подмен — для
  причин без нагрузки, а отправить вместо списка слово `handover` значило бы сказать модулю
  неправду о смене сети вместо данных. Не объявил `dns` в `hostEvents` → не получает ничего;
- на `netlost` не шлётся: сети нет — списка тоже нет;
- пустой список (`dns=`) слать нельзя и принимать не нужно: затереть рабочие резолверы пустотой
  строго хуже, чем не трогать их. Хост не отправляет такое событие, модуль его игнорирует;
- вместе со списком обязан быть **сброшен DNS-кэш**: записи получены через прежнюю сеть (в
  частности, её split-horizon адреса) и к новой отношения не имеют.

⛔ **Обработчик для `dns=` писать не нужно.** Канонный резолвер (`newProtectedResolver`) подписан
на список хоста в своём конструкторе — и новый список, и сброс кэша доезжают до него сами. От
модуля требуется ровно одно: объявить `"dns"` в `hostEvents` дескриптора, иначе хост событие не
пришлёт. Это объявление, а не код, и его отсутствие видно прямо в `module.json`. Своя реализация
резолвера — единственный случай, когда обработчик нужен; тогда и сброс кэша на вас.

Ключ дескриптора **`hostEvents`** — список причин, которые модуль разбирает. Не объявил причину →
хост подменяет её на `handover`, и модуль ведёт себя ровно как до появления причин. Поэтому:

- `handover` в множестве **всегда** (хост добавляет его сам) — он был единственным событием, и
  понимать его обязан любой модуль с `"signal"`;
- подмена односторонняя: незаявленная причина деградирует до `handover`, но причины, которой
  модуль не объявлял, он **не получит никогда** — можно разбирать строку без `default`-ветки;
- ⚠ поэтому «промолчать в ответ на незнакомое» — не вариант для хоста: `EVENT_ACK` подтверждает
  получение любого события, так что необъявленная причина выглядела бы доставленной, и
  cold-restart, которым хост страхует неуспех, уже не случился бы.

Цена отсутствия причин измерима на реальном обрыве: модуль, для которого «событие» значит только
«сеть сменилась», на пропаже сети досиживает свой стартовый бюджет (у OpenFlux — 90 с), умирает с
«transport did not come up», хост поднимает его заново — и так весь обрыв. Знающий `netlost`
просто ждёт `netback`.

#### Событие `stop` — последнее слово модуля перед остановкой

По тому же каналу, что и `handover`, хост шлёт `stop` — «сейчас вас остановят». Обрабатывать
его обязан только модуль, который держит состояние **на своей стороне сервера** и должен его
освободить: иначе сервер узнает об уходе лишь по собственному таймауту простоя, а всё это время
будет считать мёртвую сессию живой. Живой пример — qWDTT в raw-режиме: сервер раздаёт обратный
трафик round-robin'ом по зарегистрированным воркерам устройства и вычищает запись только через
90 с, поэтому следующая сессия того же устройства теряла до половины downlink'а.

- Событие **опционально**: модуль, который его не знает, просто игнорирует — как и любое другое
  неизвестное событие. Старый модуль с новым хостом работает без изменений.
- Модуль, который его обрабатывает, обязан **сам ограничить себя сверху**: хост даёт окно, а не
  бесконечность. Разумная форма — свернуть работу, отправить прощание и выйти.
- ⚠ **Гарантии доставки нет и быть не может**: процесс может умереть от OOM, SIGKILL извне или
  падения. `stop` — оптимизация, а не замена серверному таймауту простоя.

| | Android | Desktop |
|---|---|---|
| как приходит | `antinet_module_event("stop")` — вызов синхронный, пауза на прощание достаётся хосту даром | строка `stop` в stdin |
| сколько ждёт хост | ровно столько, сколько модуль держит вызов | до 1 с добровольного выхода процесса, и только у модулей с `handoverMode:"signal"` — успех записи в пайп не доказывает, что с той стороны читают |

> **⚠ Канал события — по платформе, но режим уважают обе.**
> - **Android**: C-ABI-экспорт `antinet_module_event("<причина>")` (§2.12). Сигналов тут нет: в
>   слот-процессе под ART POSIX-сигналы недетерминированы.
> - **Desktop (Windows/Linux/macOS)**: **построчный `stdin`** — хост пишет `<причина>\n` в тот же
>   канал, которым уже доставляет `ACTION_RESULT|…` (§2.7). Это не сигнал, поэтому отсутствие
>   POSIX-сигналов на Windows роли не играет. `SIGUSR1` десктоп-хост не шлёт вообще.
>
> Оба хоста ведут себя одинаково: `"signal"` → событие без убийства процесса, и только неуспех
> (процесс мёртв / канал не принял) роняет его в kill+relaunch.
>
> ⛔ **Отсюда обязанность автора**: объявили `"signal"` — реализуйте оба транспорта (Android-экспорт и
> desktop-читатель stdin), иначе на десктопе модуль не узнает о смене сети вовсе. Готовый
> desktop-читатель даёт канон `shared/lifecycle` (`startHostEventReader`) — писать свой не нужно.
>
> Цена cold-start'а на хендовере (когда режим `"restart"`) снимается контрактом восстановления
> (§2.3, callout «Контракт восстановления состояния»: `START_REASON=handover` + переиспользование
> сохранённых кредов).

**Контракт `"signal"`** — helper обязан:
1. **принимать событие обоими транспортами**: на Android — экспорт `antinet_module_event("<причина>")`
   (§2.3), на десктопе — построчный читатель `stdin` (`startHostEventReader` в референс-модулях);
   оба пути обязаны сходиться в одну функцию (`handleHostEvent`), чтобы реакция была описана один
   раз. `signal.Notify(ch, unix.SIGUSR1)` допустим как дополнительный best-effort-вход, но ни один
   хост сигналов не шлёт — на нём одном модуль событий не получит;
1-bis. **подтверждать приём строкой `EVENT_ACK|<event>`** в stdout — первым делом в
   `handleHostEvent`, до собственно реакции (подтверждается получение, а не завершение — реакция
   бывает долгой). Имя события обрезай по первому `|`: `ACTION_RESULT|<id>|<payload>` подтверждается
   как `EVENT_ACK|ACTION_RESULT`, иначе секрет уедет в `helper.stdout.log`.
   **Зачем**: на Android приём доказывает возврат C-ABI-вызова (`rc==-2` = обработчика нет → хост
   падает в cold-restart), а десктопный канал однонаправленный — «байты записаны в stdin» не
   доказывает ничего, и модуль, объявивший `"signal"` без читателя, молча остался бы без события,
   при этом отменив себе cold-restart. Десктопный хост ждёт подтверждения до 2.5с (полтора цикла
   тейла stdout) и без него делает kill+relaunch. Android лишнюю строку просто игнорирует, поэтому
   код у модуля один на обе платформы;
2. на сигнал — **полностью переустановить** долгоживущие сеть-сокеты/сессии: создать **новые**
   сокеты (protect-callback хоста привяжет их к текущему интерфейсу), переиспользуя лишь **дорогой
   cold-state** (креды/сессия/MTU — что валидно и переживает в памяти процесса) → без cold-start.
   Это не частичный in-place reset — старые сокеты к ушедшей сети должны быть закрыты и пересозданы.
3. **⚠ SOCKS5-листенер держать на том же порту через session-restart.** На это AntiNet даёт
   `signal`-модулю **фиксированный** порт (`LISTEN_PORT=P>0` в config'е — для `"signal"`
   ядро выделяет свободный порт заранее, не эфемерный 0). Ваш обработчик обязан ре-биндить
   **именно этот сконфигурированный порт** (не брать эфемерный 0 заново) — иначе AntiNet-outbound
   целится в старый порт → туннель мёртв, даже если резолверы/сессия успешно переустановились.
   Грабли реальные, а не теоретические: session-restart, берущий эфемерный порт заново, меняет его
   (напр. 42599→32813) и рвёт туннель, хотя сам модуль отработал успешно. Идеал (qWDTT): SOCKS+localConn на
   `127.0.0.1` вообще не трогать на session-restart (re-spawn только сетевого транспорта).

```go
// Одна реакция, два транспорта — оба сводятся в handleHostEvent (шаблон всех трёх референс-модулей).
func handleHostEvent(event string) {
    emitEventAck(event) // EVENT_ACK|<event> первым делом: подтверждаем приём, не реакцию
    if h := hostEventHandler; h != nil {
        h(event)
    }
}

setHostEventHandler(func(event string) {
    switch event {
    case "handover":
        // отменить текущие сетевые сессии → переустановить на новой сети (новые сокеты),
        // реюз кэш-кредов/сессии (в памяти) → без логина/капчи. Пример — qWDTT helper.go:
        // cancel ctx транспорта → re-spawn воркеров (WG/SOCKS на 127.0.0.1 переживают).
    case "netlost":
        // сети нет: поднять флаг, свернуть дозвоны, не жечь стартовый бюджет.
    case "netback":
        // сеть вернулась: снять флаг и пробовать сразу, не досиживая backoff.
    case "stall":
        // сеть та же, но релей молчит — передозвониться, не трогая cold-state.
    }
    // Причины, не объявленной в `hostEvents`, здесь не будет: хост шлёт вместо неё `handover`.
    //
    // ⚠ Ветки для `dns=<ip,…>` здесь нет намеренно: список забирает канон и сам доносит его до
    // резолвера вместе со сбросом кэша. От вас — только `"dns"` в `hostEvents` дескриптора.
    // Ветка нужна ровно в одном случае: у вас ещё один потребитель того же списка, про который
    // канон не знает (у OpenFlux это bootstrap-резолвер вендорного транспорта). Тогда берите
    // применённый список у резолвера, а не разбирайте событие повторно.
})
startHostEventReader() // desktop: построчный stdin; на Android — no-op (там зовут antinet_module_event)
```

**⚠ Объявляй `"signal"` только если протокол реально мигрирует in-process.** Если сервер держит
сессию на старом source-IP (новые сокеты с нового IP сервер игнорирует) — in-process re-establish
не оживит туннель; оставь `"restart"` (хост сделает полный fresh-процесс). AntiNet на `"signal"`
делает fallback на cold-restart, если процесс мёртв / сигнал не доставлен. Сигналы редки (AntiNet
дебаунсит серию флапов в один). Примеры: **qWDTT** (`"signal"` — сессия = per-TURN-allocation,
re-allocate свежая; WG/SOCKS на localhost переживают) и **echo** (`"signal"` — демо-обработчик;
passthrough без долгоживущей сессии). Серию флапов AntiNet схлопывает в один restart внутри окна
`handoverDebounceSec` (§2.10).

### 2.9. Логи helper'а (`helper.stdout.log`) — построчный таймстамп (рекомендуется)

AntiNet редиректит stdout+stderr helper'а в `<profileDir>/helper.stdout.log` через **`appendTo`** (не
truncate — история launch'ей переживает relaunch'и) и не обрабатывает строки построчно (data-plane-safe:
прямая запись в файл). Поэтому **таймстампит строки сам модуль**:
- логи (`log.Printf`) — `log.SetFlags(log.Ltime | log.Lmicroseconds)` (формат `HH:MM:SS.ffffff`);
- маркерные строки — **префикс таймстампа** тем же форматом. Писать его руками не надо: все
  маркеры печатает одна канонная точка `emitMarker` (`shared/hostproto`), и таймстамп с флашем
  ставит она. Модуль зовёт `emitProgress`/`emitLog`/`emitStatus`/`runAction` — и только.

AntiNet ловит `PROGRESS|`/`LOG|`/`ACTION_REQUIRED|`/`ACTION_CLOSE|`/`STATE_SAVE|`/`STATUS|`/`EVENT_ACK|`
через **`indexOf`/`Pos` (contains)**, не `startsWith` → таймстамп-префикс парсинг/тост не ломает
(тост = подстрока после `PROGRESS|`). Примеры — qWDTT (`emitProgress`/`emitLog`/`emitStatus`), echo, masterdns
(`startProgressInterceptor`). Маркеры для пользователя — здесь (§2.9); маркер состояния для решений хоста —
`STATUS|` (§2.13); блоб состояния модуля — `STATE_SAVE|` (§2.3, callout «Контракт восстановления
состояния»); подтверждение приёма события хоста — `EVENT_ACK|` (§2.8).

**`LOG|<текст>` (опционально)** — постоянная, листаемая запись, в отличие от `PROGRESS|` (только
transient toast на connect-пути — мид-сессионные `PROGRESS|`-строки хост структурно отбрасывает,
показать их некому). Хост дублирует `LOG|`-текст и на экран «Логи» (AppLogger/визуальный лог в
приложении), и в файл `log_*.txt` — одним вызовом на своей стороне, модулю знать об этом не нужно.
Используйте для событий, на которые пользователь может захотеть посмотреть позже (хендовер, мид-сессионное
действие, деградация/re-spawn релея) — не для высокочастотного per-connection шума (для него —
обычный `log.Printf`, который остаётся только в `helper.stdout.log`, экран «Логи» им не засоряется).
Без дедупа подряд идущих сообщений (в отличие от `PROGRESS|`) — каждое событие получает свою строку в
постоянной истории.
```go
emitLog("relay re-spawned after %d failures", n)   // канон shared/hostproto, писать его не нужно
```
Референс — `examples/moduleqwdtt` (`relayWatchdog`: re-spawn/give-up), `examples/moduleecho`
(мид-сессионное действие + хендовер), `examples/modulemasterdns` (хендовер).

> ### ⚠ Локализация текста — решает модуль, хост даёт только `APP_LANG=`
>
> AntiNet-хост никак не интерпретирует и не переводит текст, который отправляет модуль — для хоста это
> непрозрачная строка. Какой конкретно текст показать пользователю и на каком языке — целиком ваше, модульное,
> решение и ваша реализация. Но модулю всё равно нужно знать язык, чтобы это решение принять —
> для этого хост кладёт в конфиг-содержимое (то же KEY=VALUE, что `LISTEN_PORT`/`SETTING_<key>`, §2.3)
> ключ **`APP_LANG=<ru|en>`** — эффективный язык самого AntiNet (`LocaleHelper.effectiveLanguage`
> на Android / `i18n.EffectiveLang` на Desktop: явный выбор пользователя в настройках ?: системная локаль).
>
> **Модуль обязан ориентироваться на `APP_LANG`, а не читать OS-локаль сам** — пользователь мог явно
> выставить AntiNet на язык, отличный от системного, и любой текст, который модуль показывает,
> обязан совпадать с тем, что видно в самом AntiNet, а не с локалью процесса модуля.
>
> **Что именно локализуется — только payload, и это три разных приёмника:**
>
> | Что | Локализовать? | Почему |
> |---|---|---|
> | текст после тега в `PROGRESS|`/`LOG|` | **да, по `APP_LANG`** | это то, что пользователь видит тостом и на экране «Логи». Английский тост русскоязычному пользователю — дыра в локализации; правило поймано живым репортом («тосты masterdns английские») |
> | payload `ACTION_REQUIRED|<id>|<payloadB64>` и ответ `ACTION_RESULT|` | **да, по `APP_LANG`** | это диалог, который пользователю рисует хост. На проводе base64, значит любой язык безопасен для кодировки логов |
> | сами теги (`PROGRESS|`/`LOG|`/`STATUS|`/`EVENT_ACK|`…), таймстамп-префикс, `<detail>` у `STATUS|`, весь `log.Printf`/`fmt.Errorf` | **нет — ASCII/английский всегда** | теги разбирает хост; `<detail>` и `log.Printf` читает разработчик грепом по `helper.stdout.log`, а bash/grep-тулинг ломается на не-ASCII |
>
> Иначе говоря: граница проходит не по маркеру, а по приёмнику. Всё, что читает человек-пользователь, —
> на его языке; всё, что читает машина или разработчик, — ASCII.
>
> Референс — `examples/moduleecho`'s `demoStringsFor(cfg["APP_LANG"])`: один ru/en-стол и на
> `PROGRESS\|` и `LOG\|`-строки, и на подписи confirm, мид-сессионный текст, form/choice/display заголовки
> и лейблы. То же у masterdns (`mdStringsFor`/`mdS`) и qWDTT (`qwdttStringsFor`/`qwS`).
>
> ⛔ Копировать при этом нечего: сам выбор делает канон — `stringsForLang(lang, ru, en)`
> (`shared/hostproto`). Модулю принадлежат только две таблицы строк, а обёртка над каноном у него
> в одну строку и нужна лишь чтобы имя читалось на месте вызова. Своего сравнения с `"ru"` писать не надо:
> трактовку `APP_LANG` задаёт хост, и она обязана быть одна на все модули.

**AntiNet-сторона лога** (справочно): на каждый launch — датированный заголовок
`===== launch <local-dt+offset> | connect|ping-handover | scheme =====` (якорь для UTC-времён модуля) +
ротация (жёсткий потолок 512 КБ, сброс старшей половины по границе строки) на запуске и по heartbeat.
Кроссплатформенно (Android — хост отдаёт слоту путь, слот делает `dup2` своих stdout/stderr на него
до `dlopen` (O_APPEND); Desktop — `TDrainThread` дренирует pipe в тот же файл; ротация — общая
`rotateModuleLog`/`RotateModuleLog`).

### 2.10. Lifecycle-тайминги — значения от модуля, редактируемые пользователем (опционально)

Тайминги жизненного цикла helper'а **объявляет модуль**, задавая значения по умолчанию, но
**пользователь их меняет** в
карточке «Модули» (Android `ModulesScreen`, Desktop `ShowModulesDialog`) — это не захардкоженные,
спрятанные значения. Опустишь ключ в `module.json` → берётся built-in DEFAULT.

| Ключ `module.json` | DEFAULT | Что регулирует | Где применяется |
|---|---|---|---|
| `crashLoopMaxDeaths` | `5` | ≥N «быстрых» (внутри окна ниже) смертей helper'а подряд → AntiNet переходит на **backoff-ре-арм** (30→60→120→300с, эскалация по раунду, cap). **Не сдаётся навсегда** (раньше — сдавался): при возврате сети helper поднимается сам; цикл прекращает только disconnect/stopAll. | Android `superviseDeath`+`scheduleRearm`; Desktop `RelaunchDeadHelper` (внутр. backoff-loop). |
| `crashLoopWindowSec` | `15` | Окно (сек): смерть в пределах окна после launch'а считается «быстрой» (иначе счётчик и раунд backoff'а обнуляются — здоровый прогон). | там же |
| `heartbeatSec` | `120` | Период heartbeat-лога (диагностика живости helper'а: 💓 alive + uptime + хвост `helper.stdout.log`) + периодическая ротация лога. | Android `ensureHeartbeat`; Desktop `TModuleHeartbeatThread`. |
| `handoverDebounceSec` | `2` | Окно (сек) коалесинга флапа сети: серия хендоверов схлопывается в один restart (§2.8). | Android `onHandover`; Desktop `TModuleHandoverThread` (max среди живых helper'ов). |
| `pingTimeoutSec` | `20` | Потолок одного пинга конфига этой схемы. Модуль с медленным cold-start'ом (перебор резолверов, релей) поднимает; быстрый passthrough может занизить, чтобы мёртвый адрес не держал волну. **Второй потребитель — пол бюджета health-пробы уже поднятой module-сессии** (`tunnelProbeBudgetMs`): общий потолок пробы рассчитан на built-in конфиг и модулю мал, поэтому хост берёт `max(запрошенный, pingTimeoutSec)`. Отдельного ключа под это нет намеренно — цена подъёма/ответа у модуля одна. | Android `TunnelManager` (module-ветка батча) + `VpnHealthMonitor` через `ModuleManager.tunnelProbeBudgetMs`; Desktop `PingConfigs`/`DoSingleConfigPingDirect` + `TunnelProbeBudgetMs`. |
| `pingNeedsConsent` | `false` | `true` → перед каждым фоновым пингом хост спрашивает сам модуль сабкомандой `canping` (§2.2): «можешь без интерактива?». `false` → не спрашивается вовсе, ни вызова, ни цены. Ручной одиночный пинг интерактив разрешает и через этот гейт не идёт (пользователь смотрит на экран). | Android `ModuleManager.canPing`; Desktop `ModuleManager.CanPing`. |
| `relayWindowSec` | (нет) | **Опционально, только для модулей с релейным слоем** (напр. qWDTT поверх VK-TURN). Окно (сек) детекта «молчащего» релея: helper получает его как `RELAY_WINDOW_SEC` и сам реализует relayWatchdog (порог fail'ов = `windowSec/5`, мин 2 → re-spawn транспорта на текущей сети). Не объявляешь → поля в карточке нет, watchdog выкл. Модули без релея (StormDNS/echo) его не объявляют. | helper модуля (qWDTT `relayWatchdog`); UI-поле «Окно детекта обрыва». |

- **cold-start budget (READY_TIMEOUT ~95с) не настраивается** — helper поднимается сколько нужно
  (cold-перебор резолверов/капча — легитимны); прерывается только отменой коннекта пользователем.
- Override-хранилище: Android — `AppSettings.moduleCrashMaxDeaths`/`...CrashWindowSec`/`...HeartbeatSec`/
  `...HandoverDebounceSec`/`...RelayWindowSec` (`Map<moduleId,Int>` — идентичность модуля это имя его
  каталога, см. §2.1); Desktop — `settings.json` те же ключи (`Map<scheme,Int>`).
  Эффективное значение = `override>0 ? override : declared>0 ? declared : DEFAULT`.

### 2.11. Настройки модуля — декларативные, редактируемые пользователем (опционально)

Модуль декларирует **произвольные настройки** в `module.json` → AntiNet показывает их типизированными
контролами в карточке «Модули» (Android `ModulesScreen`, Desktop `ShowModulesDialog`), хранит per-module
override и **передаёт helper'у при запуске** как `SETTING_<key>=<value>` строкой в том же
конфиг-содержимом, что `LISTEN_PORT`/`LINK` (content-based доставка, §2.3 — не файлом). Так пользователь
управляет поведением модуля без правок кода (напр. qWDTT: режим решения VK-капчи).

**Значение всегда строка**, каким бы ни был `type`: `bool` → `true`/`false` строчными (так пишут и
значение по умолчанию из декларации, и переключатель в карточке — на обеих платформах), `int` →
число, `enum` → `value` варианта. ⛔ **Булево читайте каноном `parseBoolSetting`**
(`shared/hostproto`), а не
сравнением с литералом: неразобранная настройка не отказывает, она молча становится `false`, и
отличить это от «пользователь выключил» уже нечем.

**Декларация (`module.json`):**
```json
"settings": [
  { "key": "captchaMode", "type": "enum", "label": "Решение VK-капчи", "default": "auto",
    "description": "…", "options": [ { "value": "auto", "label": "Авто" }, { "value": "wv", "label": "Только webview" } ] },
  { "key": "showDialog",   "type": "bool",   "label": "Показывать диалог", "default": true },
  { "key": "dialogText",   "type": "string", "label": "Текст",            "default": "Привет" },
  { "key": "autoCloseSec", "type": "int",    "label": "Автозакрытие (сек)","default": 0, "min": 0, "max": 600 }
]
```

| Поле | Назначение |
|---|---|
| `key` | идентификатор → ключ `SETTING_<key>` в конфиг-содержимом. Обязателен. |
| `type` | `bool` (Switch) / `int` (число + `min`/`max`) / `string` (текст) / `enum` (dropdown + `options`). |
| `label` | подпись контрола. |
| `default` | значение по умолчанию **строкой** (bool: `true`/`false`; int: число; enum: один из `options[].value`). |
| `description` | опц. подсказка под контролом. |
| `options` | enum: список `{value,label}` (показывается `label`, хранится/передаётся `value`). |
| `min`/`max` | int: границы (ввод clamped). |

**Поток:** `build.py` сериализует массив в meta-data `com.antinet.module.settings` (Android, JSON-строкой) +
dist `module.json` (Desktop, as-is) → AntiNet парсит → рисует контролы → пользователь правит → значение хранится
(Android `AppSettings.moduleSettings: Map<pkg, Map<key,String>>`; Desktop `settings.json moduleSettings
[scheme][key]`) → при launch добавляется `SETTING_<key>=<value>` (override ?: default) в то же
конфиг-содержимое → **helper читает тем же парсером**, что `LISTEN_PORT`/`LINK`.

```go
// helper parseConfig:  case "SETTING_captchaMode": cfg.CaptchaMode = v
mode := cfg.CaptchaMode    // "" → ваше значение по умолчанию (AntiNet всегда шлёт значение, но будьте готовы к пустому)
```

- **AntiNet значения не интерпретирует** (агностичен) — семантику владеет модуль. Битая декларация → набор
  настроек пуст (backward-compat: модуль без `settings` работает как раньше).
- Примеры: `examples/moduleecho` (bool/string/int → демо-диалог `DemoActionActivity`),
  `examples/moduleqwdtt` (enum `captchaMode` → `setCaptchaMode`, §2.7-капча).
- **Антипаттерн (запрещён)**: хардкодить в helper'е то, что пользователю логично менять (режим капчи, тайминги,
  флаги) — объявляй настройкой; читать `SETTING_*` иным путём, чем общий cfg-парсер.

### 2.12. Backend у модуля ровно один — нативный

Модуль — всегда настоящий машинный код со своим сетевым стеком и реальными OS-потоками: Android —
c-shared `.so`, грузится `dlopen`'ом в зарезервированный слот-процесс (§2.1/§2.3); Desktop —
обычный форкнутый бинарь. Никаких host-функций для сети ему не нужно: он сам дозванивается, сам
резолвит DNS, сам разбирает SOCKS5.

⛔ **`.wasm`-backend не поддерживается.** Ключи `helperBinary.wasm`, `build.wasmGoPkg`,
`wasmSessionModel`, `wasmEngineMode`, `wasmVersion`, `wasmUpdateUrl` не читает ни одна платформа, а
дескриптор, объявляющий для одной схемы и нативный бэкенд, и `.wasm`, **отклоняется целиком** с
ошибкой в лог — молча затенить нативный бэкенд устаревшим `.wasm` нельзя.

### 2.13. `STATUS|<state>[|<detail>]` — типизированное состояние живого helper'а (рекомендуется)

Тот же построчный канал stdout, что `PROGRESS|`/`LOG|` (§2.9, тот же таймстамп-префикс, тот же
contains-парсинг), но **не текст для пользователя, а вход решения хоста**. Хост читает только `<state>` из
закрытого перечня; `<detail>` — свободная ASCII-строка, попадает лишь в лог.

```go
func emitStatus(state, detail string) {
    // '|' — разделитель, перенос строки — конец записи: и то и другое из detail'а убирается.
    detail = strings.ReplaceAll(strings.ReplaceAll(detail, "|", "/"), "\n", " ")
    if detail != "" {
        fmt.Printf("%s STATUS|%s|%s\n", time.Now().Format("15:04:05.000000"), state, detail)
    } else {
        fmt.Printf("%s STATUS|%s\n", time.Now().Format("15:04:05.000000"), state)
    }
}
```

| `<state>` | Значение | Что делает хост сегодня |
|---|---|---|
| `ok` | работает штатно | снимает `waiting`/`fatal`: нудж снова считается осмысленным |
| `waiting` | жив, но ждёт **внешний** ресурс (квота, очередь, снятие rate-limit) | **пропускает лестницу нуджей и эскалирует к relaunch'у сразу** |
| `degraded` | работает, но хуже обычного | только запоминает и логирует (решения на него пока не завязаны) |
| `fatal` | сам не поднимется, нужно пересоздание/вмешательство | как `waiting` |

- **Состояние липкое до следующего маркера.** Прислал `waiting` — обязан прислать `ok`, когда ресурс
  получен, иначе хост будет пересоздавать процесс на каждом последующем отказе.
  ⚠ **Парный `ok` ставь в точку «работа пошла», а не «работа кончилась».** Референс — qWDTT:
  `emitStatus(statusWaiting, …)` в ветке квоты (`group.go`) и `emitStatus(statusOK, "")` в
  `noteDtlsEstablished` (`helper.go`), то есть на установлении транспорта. Изначально `ok` стоял на
  «сессия вернулась без ошибки» — а сессия блокирует воркер на всё время работы, поэтому её успешный
  возврат наступает уже после конца полезной работы, и `waiting` держалось бы у хоста всю сессию.
- **Дедуп — на стороне модуля.** Точка «работа пошла» обычно срабатывает часто (у qWDTT — на каждом
  из 9 воркеров и на каждой переустановке), поэтому отправлять одно и то же состояние подряд не
  нужно: печатайте строку только на смене (`lastEmittedStatus` в qWDTT). Хост дедуплицирует и сам,
  но поток
  одинаковых строк засоряет `helper.stdout.log`, который потом читают глазами.
- **Неизвестное `<state>` не запоминается** — хост пишет предупреждение и игнорирует строку.
  Расширить перечень со стороны модуля нельзя: молча «увести себя в неизвестность» не получится.
- **Модуль, который маркер не шлёт, ничего не теряет** — хост откатывается на эвристику по хвосту
  `helper.stdout.log` (подстроки `quota`/`error 486`/`waiting: turn`). Она существует ровно ради
  таких модулей и хрупка к любой смене формулировки — шли маркер, не полагайся на неё.
- Текст `<detail>` — **только ASCII** (то же жёсткое требование, что для `PROGRESS|`/`LOG|`, §2.9:
  строка ложится в `helper.stdout.log`, который читает grep-тулинг).

**Почему это маркер, а не сабкоманда.** Спавн-глаголов у модуля три (`summarize`/`normalize`/
`canping`, §2.2), и `status` четвёртым не стал намеренно: спавн поднимает отдельный процесс без
состояния сессии — он не знает ни про исчерпанную квоту текущего аккаунта, ни про то, сколько
воркеров сейчас в ретрае. Отвечать на такой вопрос может только **живой** helper, и знает он ответ
ровно в момент события, а не когда хост спросит. Опрос живого процесса потребовал бы второго
канала (сокет/сигнал) там, где уже есть работающий однонаправленный stdout.

**Потребитель на стороне хоста** (справочно): Android
`ModuleManager.moduleReportsUnrecoverableByNudge` → гейт `nudgeIsPointless` в
`VpnHealthMonitor.probeAndRecoverPinned`; Desktop — одноимённые
`ModuleManager.ModuleReportsUnrecoverableByNudge` / `TVpnHealthMonitor`. Без гейта отказ по квоте
проходил всю лестницу бэкоффа (30/60/120/180/300с) и добирался до настоящего relaunch'а лишь на
пятой попытке — через ~11.5 минут мёртвого туннеля.

## 3. Жизненный цикл (сторона AntiNet — справочно)

1. **discover** — скан `<antinet>/modules/<id>/module.json` → регистрирует handler на каждую `scheme`.
2. **parse** (импорт ссылки) — `myproto://…` → `VpnConfig` (непрозрачная ссылка в `ext`); имя/сервер
   карточки — из `summarize()`.
3. **connect / ping** — хост поднимает слушающий SOCKS5-сокет и отдаёт его модулю вместе с конфигом
   (KEY=VALUE+LINK; модуль самодекодит LINK) → ждёт маркер `ready` → SOCKS5-outbound на
   `127.0.0.1:<port>` с per-session кредами. Порт известен хосту сразу, он же владелец сокета.
4. **события сети** — по `handoverMode`: `"signal"` → уведомление модулю с причиной
   (`handover`/`netlost`/`netback`/`stall`, §2.8; `antinet_module_event` на Android / строка в
   stdin на десктопе), иначе и на неуспех `handover` — kill+relaunch; порт не меняется, сокет
   переживает рестарт модуля. `netlost`/`netback`/`stall` перезапуска не влекут вовсе.
5. **teardown** (disconnect / конец пинга) — модуль останавливается; сокет и protect-сервис гасятся.

**Ограничения модуля:**
- Module-конфиг **не может быть каскадом** (2-й хоп): его socks локален (`127.0.0.1`), как удалённый
  хоп недостижим. Основой (primary) — может.
- Пинг модуля = старт helper'а (может быть долгим, если протокол требует «прогрева») —
  `parallelPing=false` → последовательно, не блокируя параллельный пинг обычных конфигов.

## 4. Кроссплатформенность

**Контракт платформо-агностичен** в своей сути:
- ссылка → `[config, resolvers]` + `[name, server]` (parse-only);
- helper = SOCKS5-листенер + стабильный порт + аргументы `config/resolvers/profileDir/protectPath`.

**Платформо-специфичны ровно 4 механизма** (Android-only), и все четыре — каноны: build-тегами
внутри них занимается `shared/`, модуль зовёт одно и то же имя на обеих платформах.

| Абстракция | Канон | android | !android (десктоп) |
|---|---|---|---|
| `dieWithParent()` | `shared/lifecycle` | `unix.Prctl(PR_SET_PDEATHSIG, SIGKILL)` | no-op (хост-процесс убивает helper сам) |
| `protectFromOomKill()` | `shared/lifecycle` | `os.WriteFile("/proc/self/oom_score_adj", "-1000", …)` — defense-in-depth (§2.3: хост и так держит слот `BIND_IMPORTANT`) | no-op (нет Android LMK-модели) |
| `startHostEventReader()` | `shared/lifecycle` | no-op (модуль — библиотека, stdin ему не адресован) | построчный читатель `stdin` → `handleHostEvent` — единственный канал событий хоста на десктопе (`handover`, `ACTION_RESULT\|…`) |
| protect-адаптер: `dialControl(protectPath, *protectStat)` (форма `net.Dialer.Control`) и `protectFdFunc(protectPath)` (форма `func(fd int32) bool`) | `shared/protect` (android) + `shared/offtun` (десктоп) | SCM_RIGHTS на UNIX-сокет AntiNet | bind сокета к физ-интерфейсу |

⚠ **Сигналов (`SIGUSR1` и любых других) хост не шлёт ни на одной платформе** — обработчик заводить
незачем. На Android сигнал в слот-процессе под ART недетерминирован, поэтому хост зовёт
C-ABI-экспорт; на десктопе он пишет строку в stdin.

**Форм protect-хука ровно две**, потому что столько их бывает у хуков реальных data-plane
библиотек: `net.Dialer.Control` (echo, qWDTT, OpenFlux) и `func(fd int32) bool` (её хочет
`nativeclient.Options.Protect` у masterdns). Обе канонные, обе под одним именем на обеих платформах.

**Что остаётся модулю: ничего платформенного.** Файлов вида `platform_android.go`/`platform_other.go`
у модуля быть не должно — ни одного, как и собственных точек входа. Проверка простая: **любой
`//go:build`-тег в дереве модуля означает, что что-то не вынесено** (исключение — вендоренный
чужой код внутри `internal/`, его каноникализировать нечем).

- **Android** (есть): `.so` (`c-shared`) + `module.json` в `files/modules/<id>/`, грузится `dlopen`'ом в
  зарезервированный слот-процесс; off-TUN через SCM_RIGHTS (`VpnService.protect`); хендовер — C-ABI
  `antinet_module_event` (не SIGUSR1: в слоте под ART доставка сигнала недетерминирована, §2.8);
  lifecycle ведёт хост (слот — Android-компонент, не форкнутый ребёнок). Сборка GOOS=android (см. §5).
- **Desktop** (windows/linux/darwin): тот же helper-код, `go build` под нужную ОС. lifecycle ведёт
  хост-процесс (Pascal `TProcess`); хендовер — событие в `stdin` при `handoverMode:"signal"`, иначе
  (и на неуспех события) kill+relaunch → `dieWithParent`/`installHandoverHandler` no-op на всех
  desktop-ОС, а события принимает `startHostEventReader`. **off-TUN-protect реальный (не nil!), но не дублируется в модуле** — канон в
  **`shared/offtun/`** (Linux `SO_BINDTODEVICE` / Win `IP_UNICAST_IF` / macOS `IP_BOUND_IF`;
  физ-iface исключает AntiNet-TUN `172.19.0.0/28`). build.py инжектит `offtun_*.go` в main-пакет helper'а
  перед сборкой и удаляет после, безусловно — в git per-module их нет, third-party-модуль получает off-TUN
  бесплатно. Обёртку под protect-хук своей data-plane либы модуль тоже не пишет: обе формы адаптера
  канонные и называются одинаково на обеих платформах — `dialControl(protectPath, *protectStat)` (форма
  `net.Dialer.Control`) и `protectFdFunc(protectPath)` (форма `func(fd int32) bool`); десктопная половина
  живёт в `shared/offtun/offtun_adapter.go` и зовёт `offtunBindControl`/`offtunBindFd`, android-половина —
  в `shared/protect/protect_adapter_android.go` и зовёт `protectViaService`. Модулю остаётся вызов.
  Требование: `go.mod` модуля содержит `golang.org/x/sys`. **Почему не sing-box
  `process_name→direct` одного**: process-attribution ненадёжна для эфемерных UDP-DNS-сокетов, а если
  правило `port:53→hijack-dns` окажется выше per-app bypass, резолвер-UDP DNS-туннелей (на :53)
  перехватывается до bypass и не доходит (live: StormDNS 0/15 `UPLOAD_MTU value=0` → ∞ CONNECTING;
  qWDTT recovery-re-auth `src 172.19.0.1->...:53 i/o timeout`, пин не самовосстанавливался). Socket-bind
  к физ-iface делает off-TUN независимым от routing/hijack/состояния туннеля; применяется на любом
  запуске helper'а (connect и ping). Best-effort (нужен CAP_NET_RAW/админ; фейл → обычный dial).
  ⚠ Desktop-хост `process_name→direct` при этом ставит — первым правилом, до DNS-hijack (`singboxconfiggenerator.pas`,
  имена берутся из `ModuleManager.LiveHelperBinaries`), и в таком порядке оно работает. Это второй
  эшелон, а не замена канону: порядок правил — условие его работы, тогда как `shared/offtun` от порядка
  не зависит вовсе. На Android аналога нет и быть не может — модуль живёт в слот-процессе того же
  пакета, поэтому per-package исключение неприменимо и `modulePkgs` в `applyAppRouting` пуст намеренно.
  Детали — `shared/offtun/README.md`.

#### Канон-инъекции `shared/` — общий Go-код, которого в модуле нет

Тот же приём, что у `offtun`, применён ко всему, что иначе жило бы независимыми копиями в каждом
модуле. `build.py` копирует канон в main-пакет helper'а перед `go build` и удаляет после — в дереве
модуля (и в его патче) этих файлов нет; правится только канон.

| Канон | Когда инжектится | Что даёт модулю | Что обязан сделать модуль |
|---|---|---|---|
| `shared/lifecycle/` | **всегда** (гейта нет — нужен каждому на обеих платформах) | примитивы жизненного цикла helper'а: `dieWithParent`, `protectFromOomKill`, `startHostEventReader` (десктопный приём событий хоста построчным stdin; на android — no-op), `writeReady(dir, port)` (маркер готовности `ready` + `socks.port`, атомарно) | ничего: просто зови их из общего тела helper'а. `go.mod` нужен `golang.org/x/sys` (android-половина зовёт `unix.Prctl`) |
| `shared/protect/` | **всегда** (гейта нет — на Android нужен каждому) | клиент protect-сервиса AntiNet: `protectViaService(path, fd, *protectStat)` — SCM_RIGHTS через UNIX-сокет, раздельные бюджеты ретрая для «обрыва» (`isTransientProtectErr` → немедленный повтор, плотный backoff до 250мс) и «сервиса нет» (5 попыток по 60мс), проверка ack-байта (не только длины ответа). Плюс android-половина **обоих protect-адаптеров**: `dialControl`/`protectFdFunc` | ничего: зовите `dialControl(protectPath, &pst)` там, где ваша библиотека хочет `net.Dialer.Control`, либо `protectFdFunc(protectPath)` — где `func(fd int32) bool` |
| `shared/hostproto/` | **всегда** (гейта нет — без него не работает ни один модуль) | протокол разговора с хостом целиком: `readConfigForEntry`/`parseConfig` (KEY=VALUE), `openListener` (усыновление переданного fd либо bind по `LISTEN_PORT`), маркеры `emitProgress`/`emitLog`/`emitStatus`(+`status*`)/`emitEventAck`/`emitActionClose` с таймстампом и дедупом (печатает их одна точка `emitMarker` — своего `fmt.Printf` с маркером писать не надо), `handleHostEvent`+`setHostEventHandler`, `runAction`/`awaitActionResult`, `stringsForLang(lang, ru, en)` — выбор языковой таблицы по `APP_LANG` | ничего. ⚠ Имя `parseConfig` занято каноном: разбирать KEY=VALUE хоста своим циклом нельзя — формат задаёт хост; свой парсер законен только для своего формата и называется иначе (masterdns — `parseStormDnsConfig`) |
| `shared/entry/` | **всегда** (гейта нет) | точки входа: android — `main(){}` + C-ABI-экспорты `antinet_module_run`/`antinet_module_event`/`antinet_module_call`/`antinet_module_free`; десктоп — `main()` с разбором argv, сабкомандами и `ANTINET_LISTEN_FD` | определить две функции, которые канон зовёт: `realMain(configContent, resolversPath, profileDir, protectPath string, listenFd int) int` и `moduleCall(verb, arg string) string` |
| `shared/offtun/` | **всегда** (гейта нет — десктопная половина protect нужна каждому) | off-TUN bind сокета к физ-iface на desktop (`offtunBindControl`/`offtunBindFd`) плюс десктопная половина обоих адаптеров: `dialControl`/`protectFdFunc` — те же имена, что даёт android-половина в `shared/protect/` | ничего, кроме `golang.org/x/sys` в `go.mod` |
| `shared/socks5/` | `"socks5": true` | SOCKS5-протокол целиком: `socksHandshake` (приветствие + user/pass RFC 1929 + разбор запроса → `socksRequest`, отказы отвечает сам), `serveSocksListener` (accept-петля: транзиентную ошибку переживает, закрытый листенер завершает), `relayBidi`+`relayCopy` (реле с честной политикой закрытия: обрыв апстрима → RST, а не фальшивый EOF), `serveSocksUDPAssociate` (UDP-реле RFC 1928 §7 со счётчиками и `readyCh`), `socksRep`, `socksReadLP`, `parseSocksUDP`, `buildSocksUDPHeader` | реализовать `socksUDPTransport` (`LookupHost` + `DialUDPTarget`) и свой CONNECT-дозвон — то есть ровно транспорт, у каждого модуля свой (через туннель / off-tunnel под protect'ом). Недостижимую семью адреса вернуть как `errSocksTargetUnreachable` — канон ведёт для неё отдельный счётчик |
| `shared/dns/dnsshim_*.go` | **всегда** (гейта нет — абстракция от ОС, а не опция) | прокладка к резолверам: `protectedNetResolver(serversFn, protectPath) *net.Resolver` — стандартный тип, который принимают `net.Dialer.Resolver`, `http.Transport` и сам `net.DefaultResolver`; `systemResolver(protectPath)` — то же поверх резолверов ОС; `systemDNSServers()` — их список (`/etc/resolv.conf` на unix, `GetAdaptersAddresses` у физ-адаптера на Windows, присланный хостом — на Android); `normalizeDNSServers`/`normalizeDNSCsv`. Протокол DNS ведёт Go, прокладка даёт только сокет — отсюда даром TCP-повтор на усечённом ответе и разбор CNAME | ничего, кроме своего `dialControl(protectPath, *protectStat)` |
| `shared/dns/dns_*.go` | `"dnsResolver": true` | protected off-tunnel резолв ваших dial-таргетов: `newProtectedResolver(cfg["DNS_SERVERS"], protectPath)` → `LookupHost` (TTL-кэш + single-flight + прямой UDP A/AAAA-запрос к физическим DNS сети). Сигнатура `LookupHost` — та же, что ждёт `socksResolver` канона socks5 | ничего, кроме своего `dialControl(protectPath, *protectStat)` (он у вас и так есть, §4-таблица выше) |

**Зачем гейт у двух из восьми**: `lifecycle`, `protect`, `offtun`, `hostproto`, `entry` и
`dnsshim` нужны любому модулю без исключений — без них helper не запускается, не разговаривает с
хостом и не может резолвить, не уходя в TUN, поэтому безусловны; `socks5` и `dns_*.go` —
опциональные возможности, и лишний инжект тянул бы в чужой `go.mod` зависимости ради кода,
который модуль не зовёт. У masterdns SOCKS живёт внутри вендоренного апстрима
(`internal/client/socks_*.go`) — туда канон не тащим, это чужой код.

⚠ **Прокладка и кэширующий резолвер — разные вещи, и гейт только у второго.** Кэш dial-таргетов
не нужен модулю, который свои цели резолвит внутри уже поднятого туннеля (qWDTT — через свой
netstack): там изоляция от TUN дана самим туннелем. Но резолвить снаружи туннеля приходится
почти каждому — хотя бы чтобы дозвониться до собственного входа, пока туннеля ещё нет (у qWDTT
это VK-auth, у OpenFlux — хост документа), и вот для этого прокладка нужна всем. Поэтому она и
инжектируется безусловно: за флагом «мне нужен кэш» доступ к резолверам ОС оказаться не может.

⛔ **Копию канона в своём дереве не заводи.** Канон — единственный экземпляр общей механики; всё, что
дублирует его у себя, неизбежно с ним расходится, и расхождение обнаруживается не в сборке, а в
рантайме на чужой машине. Нужна другая форма вызова — напишите тонкий адаптер под свою data-plane
библиотеку, но механику зови канонную.

> Держите в `main.go` лишь обращения к `dieWithParent()` / `startHostEventReader()` /
> `net.Dialer{Control: dialControl(protectPath, &pst)}` — тогда один и тот же helper собирается под Android
> и под любую десктоп-ОС без `#ifdef`-мусора в основной логике. `moduleecho` кросс-компилируется под
> android/windows/linux/darwin.

> ⚠ **Антипаттерн (грабли реальные)**: индирекцию не заводи как package-level `var X func(...)`,
> заполняемую отдельным `init()` в другом файле — легко написать `var` и зовущего его caller'а, а сам
> `init()` не написать. Именно это и случилось в qWDTT: две такие переменные были объявлены, `creds.go`
> безусловно звал одну из них на каждом VK-auth-запросе, а заполняющий их `init()` жил в файле,
> которого не существовало нигде в дереве. Результат — `panic: invalid memory address or nil pointer
> dereference` (SIGSEGV) на первом же обращении, каждый раз, без единого успешного старта; `go build`
> при этом проходил чисто (компилятор не проверяет, что переменная-функция заполнена до первого
> вызова рантаймом — это не type error, а nil-dereference).
>
> Значение на объявлении (`var X FuncType = realImpl`) этой дыры не имеет: потеря реализации станет
> ошибкой сборки, а не рантайма. Обычная функция — тем более.
>
> `moduleecho` (эталон выше) структурно иммунен к этому классу целиком: `dialControl(protectPath, st)`
> — обычная функция с явным параметром на каждом call site (`net.Dialer{Control: dialControl(protectPath,
> &pst)}`), не глобальная переменная, ждущая отдельного шага инициализации где-то ещё. **Предпочитай
> echo's форму (explicit-parameter function) везде, где возможно** — платформенная развилка живёт
> внутри самой функции (в канонах `shared/protect/` и `shared/offtun/` лежат разные тела под
> build-тегами), вызов которой не может оказаться nil.

#### DNS и protect — что чем резолвится и почему нельзя иначе

**Правило одной строкой: модуль никогда не резолвит через `net.DefaultResolver` как он есть.**
Либо канонная прокладка, либо ничего.

**Почему.** На Android Go по умолчанию берёт cgo-резолвер (`goosPrefersCgo`, golang/go#10714), а
тот не проходит через `net.Dialer` — ни одного хука, значит сокет нечем защитить. Под VPN такой
запрос уходит в TUN, то есть в туннель, который держится на самом модуле: резолв ждёт транспорта,
транспорт ждёт резолва. Ретраем это не лечится, потому что состояние устойчиво.

**Почему `PreferGo: true` и почему адрес от Go игнорируется.** `PreferGo` включает чистый
Go-резолвер — только у него есть хук `Dial`, в котором сокет и защищается. Но Go при этом читает
`/etc/resolv.conf`, которого на Android нет: `dnsReadConfig` падает на захардкоженный `defaultNS`
= `127.0.0.1:53`, где никто не слушает. Поэтому прокладка адрес, который просит Go, **отбрасывает**
и сама выбирает, куда слать. Своими руками этого писать не нужно — это и есть канон.

**Откуда берутся серверы.**

| источник | что это | когда |
|---|---|---|
| `DNS_SERVERS` (конфиг) | физические DNS сети, которые хост прочитал у ОС | при старте helper'а |
| событие `dns=<ip,...>` (§2.8) | они же, но актуальные | на каждой смене сети |
| `systemDNSServers()` | резолверы самой ОС: `/etc/resolv.conf` на unix, `GetAdaptersAddresses` физ-адаптера на Windows, **список от хоста на Android** | когда своих нет |
| своё (пресет, bootstrap) | выбор пользователя либо зашитый список модуля | как решит модуль |

**Android — не исключение, а другой путь доставки.** Изнутри процесса резолверы системы там взять
неоткуда: `/etc/resolv.conf` не существует, а netd под VPN резолвит в туннель. Но сами адреса
известны хосту — он читает их у платформы (`LinkProperties.dnsServers` физической сети), и
системный резолвер Android берёт их из того же источника. Поэтому на Android `systemDNSServers()`
возвращает список, присланный хостом: это не замена резолверам ОС, а буквально они.

Забирает список сам канон — `parseConfig` (конфиг при старте) и `handleHostEvent` (событие `dns=`)
в `shared/hostproto`. **Модулю для этого делать не нужно ничего**: обязанность, за невыполнение
которой платят не отказом сборки, а молчаливой потерей фоллбэка на одной платформе, раздавать
авторам нельзя.

На Windows список берётся у физического адаптера намеренно: Wintun для `GetAdaptersAddresses`
такой же адаптер, и его DNS ведут внутрь туннеля.

**⛔ Объявил `dnsResolver: true` — объявляй и `dns` в `hostEvents`.** Иначе список приезжает
ровно один раз, при старте, и описывает сеть, которая была активна тогда. После смены сети
резолвы уходят в резолверы прежней сети и умирают по таймауту, а транспорт при этом жив —
поэтому ни переподключение, ни нудж хоста не помогают, и выглядит это как «модуль не замечает,
что сеть сменилась».

**Кода при этом писать не нужно — только объявление.** Резолвер подписывается на список хоста сам
(`newProtectedResolver`), и каждый новый `dns=` доезжает до него вместе со сбросом кэша. Обработчик
события для этого не нужен: обязанность, за пропуск которой платят не отказом сборки, а молчаливой
потерей актуальности, контракт авторам не раздаёт.

**Нечего взять — отказывайте, а не обходите.** Пустой список даёт `errNoDNSServers`. Соблазн «ну
попробуем системным резолвером Go» — это и есть путь в TUN, описанный выше.

**Protect: формы и кто их даёт.** Хук ровно двух форм, обе канонные и под одним именем на обеих
платформах: `dialControl(protectPath, *protectStat)` (форма `net.Dialer.Control`) и
`protectFdFunc(protectPath)` (форма `func(fd int32) bool`). Внутри — SCM_RIGHTS к сервису AntiNet
на Android, bind к физ-iface на десктопе. **Передавай `protectPath` параметром**, не сохраняй хук
в package-level переменную: незаполненный глобал отказывает в рантайме, а не на сборке (разбор —
в антипаттерне выше).

## 5. Сборка

**Единый вход — `build.py`** (интерактивный выбор ОС и модуля либо флаги). Список
модулей он собирает сам, сканируя `examples/*/module.json`, — реестра, который надо править руками,
нет: свой модуль достаточно положить папкой рядом с образцом, и ключом станет имя каталога без
префикса `module`.

### Секция `build` в дескрипторе

Она нужна только сборщику: в плоский `module.json` для хоста эта секция не попадает.

```jsonc
"build": {
  "goDir":  "native/<дерево>",     // где лежит Go-код модуля, относительно каталога модуля
  "goPkg":  "./cmd/helper",        // какой пакет собирать (у однофайлового модуля — ".")
  "ldflags": "-checklinkname=0",   // опц.: доп. флаги линкера, сборщик подставит их сам
  "nativeLibs": { /* опц.: доп. библиотеки рядом с helper'ом — §2.4 */ },
  "upstream": { /* опц.: координаты вендоренного апстрима для бампа — UPGRADE.md */ }
}
```

`upstream` объявляют только модули, собранные из чужого апстрима: он задаёт, откуда тянуть новую
версию и на какой ревизии дерево стоит сейчас. Процедура обновления — `UPGRADE.md`, к рантайм-контракту
она отношения не имеет.

Рядом с `build` живёт и **`license`** — SPDX-идентификатор лицензии самого модуля (по умолчанию
`MIT`). Его читает упаковщик: от него зависит лицензионный раздел авторского архива, а вложенные
`LICENSE` вендоренных деревьев он находит сам и перечисляет отдельно, не перекрывая их условия.

### Команды
```bash
python build.py                                 # полностью интерактивно
python build.py --os linux   --module qwdtt     # desktop: go build (CGO_ENABLED=0)
python build.py --os windows --module echo --arch amd64
python build.py --os android --module masterdns --abis arm64-v8a   # .so + module.json
python build.py --os all     --module qwdtt -y   # android + windows/linux/darwin
```
- **android** → делегирует `tools/build-module.py` (NDK clang → `-buildmode=c-shared` .so) →
  `examples/<module>/dist/android/<abi>/lib<name>.so` + `module.json` рядом. Gradle/SDK не нужны:
  модуль не приложение.
- **windows/linux/darwin** → `go build` (CGO_ENABLED=0 — чистая кросс-компиляция без C-тулчейна) →
  `examples/<module>/dist/desktop/<os>_<arch>/<module>-helper[.exe]`. Desktop-хост форкает его суб-процессом.

**Раздача автору + публикация:**
- `--package --module <X>` → **самодостаточный архив для автора** в `dist-archive/<X>-module-v<ver>.zip`:
  исходники модуля + этот `build.py` + `tools/` + **все каноны `shared/`** (`SHARED_CANONS`:
  `offtun`/`protect`/`lifecycle`/`hostproto`/`entry`/`socks5`/`dns` — одна таблица `CANONS` и для инжекта,
  и для упаковки, чтобы новый канон не забыли положить автору) + `MODULE_API.md`/`PORTING.md` +
  сгенерённый author-README. Автор распаковывает и собирает без репо AntiNet:
  `python build.py --module <X> --os all` (Go + NDK, больше ничего). Билд-артефакты в архив не кладутся.
- `--bundle --module <X>` → **release-бандлы для публикации** в `dist-release/`: плоский ZIP каждого
  собранного `dist/android/<abi>/` и `dist/desktop/<os>_<arch>/` (формат §2.5) + скелет манифеста
  `antinet-module.json` (`version` из `module.json`, URL'ы — плейсхолдеры). Залить ZIP'ы +
  манифест, вписать URL'ы, прописать `updateUrl` в `module.json` → авто-обновление +
  `antinet://import?module=`-установка (§2.5).

`tools/build-module.py` — низкоуровневый android-only билдер (его и зовёт `build.py` для android);
можно дёргать напрямую: `python module_system/tools/build-module.py --help`. Ручная сборка одного ABI:
```bash
NDK="$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/<host>/bin"   # <host>=windows-x86_64|linux-x86_64
GOOS=android GOARCH=arm64 CGO_ENABLED=1 \
  CC="$NDK/aarch64-linux-android26-clang"                      # на Windows: ...-clang.cmd
  go build -buildmode=c-shared -trimpath \
  -o <module>/dist/android/arm64-v8a/libmyhelper.so ./cmd/helper
```
(`build.py` дополнительно кладёт рядом `module.json` и убирает сгенерированный C-заголовок.)
Один desktop-бинарь вручную: `GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o helper ./cmd/helper`.

## 6. Версионирование

`apiVersion` (ключ `module.json`) — версия этого контракта. Она **одна: `1`**. Её объявляют все
модули, включая четыре референсных, и другой не существует.

**Ни один хост `apiVersion` не читает** (ни Kotlin, ни Pascal) — поле информационное. Жёсткая
проверка совместимости появится, когда реально понадобится отказать старому модулю; отправной
точкой тогда будет `1`.

Что означает «версия одна»: этот файл описывает контракт целиком и в настоящем времени. Если он
изменится несовместимо, `apiVersion` станет `2` и здесь появится, что именно ломается. Пока такого
не произошло — читай файл как есть, ничего «устаревшего» в нём держать не нужно.
